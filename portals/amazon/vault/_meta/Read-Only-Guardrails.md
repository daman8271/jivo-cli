# Amazon — Read-Only Guardrails (this platform's instance of the safety law)

This study touched JIVO's **live** Amazon Seller Central account. Money, live inventory, and
real orders are on the other end. This note records exactly how read-only was enforced, and the
one place the rules were widened (AMENDMENT-04) with its audit trail.

## The three-layer read-only guarantee (code-level, deny-by-default)

The live walk ran through a purpose-built Playwright harness (lead-approved permanently for this
mission) whose read-only property is enforced in **code**, not judgement:

1. **L1 — Transport gate.** Originally: abort every non-GET before the socket. **Under
   AMENDMENT-04** the gate now lets **app-fired** non-GET requests through (the app finishing its
   own render), while still hard-blocking two paths — `logout`/`sign-out` and
   `token-refresh`/rotation — for self-preservation (they would kill the study's session or break
   JIVO's e-com team's live session + keepalive cron). The study **never authors or replays** a
   request; every non-GET that fires was initiated by the page itself.
2. **L2 — Click gate (now the PRIMARY write guard).** Every candidate control's label is matched
   against a compiled **DENY** regex (save · submit · create · add · edit · update · delete ·
   approve · reject · acknowledge · confirm · cancel · launch · publish · activate · pause ·
   resume · pay · settle · dispute · upload · import · sync · generate/schedule-report ·
   invite-user · …) which **wins** over the ALLOW regex. A control inside a `<form>`, a
   `type=submit`, a disabled control, or any label with no ALLOW match is **not clicked** — it is
   recorded as `UNVERIFIED CONTROL`. With the transport gate open, *not clicking is the whole
   defence*: a mutating POST can only fire if a click fires it.
3. **L3 — Dialog gate.** `page.on('dialog')` **always dismisses**, never accepts — so a confirm
   modal can never be completed, and the automation channel never freezes.

Additionally: **never type into a form field** (search/filter boxes only), never press Enter in a
form, and per **G1** a control that cannot be classified is not clicked.

## The AMENDMENT-04 audit trail — every app-fired non-GET is logged

Because the coded transport block was widened, the **record** is complete instead:

- **`captures/nonget-allowed.tsv`** — **148 rows**, one per app-fired non-GET that passed through:
  timestamp · method · response status · initiating page · full URL · redacted request-body
  **shape** (keys/types only, values stripped per G6). This is the exact record of what JIVO's
  account experienced during the study.
- **`captures/nonget-flagged.tsv`** — app-fired non-GETs whose path *suggests* a state change
  (create/update/delete/submit/approve/pay/upload/generate/…). **This file is empty (header only):
  ZERO state-changing non-GETs fired.** The click-law held; the only non-GETs that fired are
  reads — `business-reports/api`, `homepage/casino/data`, `myinventory/gql`,
  `orders-api/countOrders`, `asin-spotlight/graphql` (all GraphQL/RPC reads) plus telemetry.

**No write was caused. No request was authored or replayed.** The 13 `READ_POST` rows in
[[Amazon-Endpoints]] are documented from these observations; the CLI (Phase 8) never wires them —
it is GET-only.

## The Amazon-specific hazards this study respected

- **Report generation is a WRITE (G2).** Requesting an ARA report (`request-report-download`),
  a PO export (`generateVendorSearchFile-v3`), or any Report-Central report *creates a row and
  burns the account's queue budget*. The study **enumerates all 35 Seller Central report types +
  the ARA/PO reports** ([[Business-Reports-Analytics]], [[Amazon-Data-Inventory]] §6) but **never
  fires one**. The GST report seen in the history was generated by JIVO's own cron, not this study.
- **Sponsored Ads / campaign state is live spend.** Never touched.
- **G9 — consume, never mint.** Seller Central's session was consumed from the existing 8-day-old
  jar; Vendor Central's expired sessions were reported `NOT_REACHABLE`, never re-logged-in (a fresh
  VC login rotates cookies out from under the 10:30 IST cron). See [[Auth-and-Access]].
- **Bot-hostility.** The harvest used one gentle attempt per asset, then app-driven navigation
  (concurrency ≤3, jitter). Tripwires for captcha / account-lock / session-invalidation / 2FA were
  armed on every navigation; **none fired** across ~65 navigations.

## What is deliberately NOT in the CLI

The generated CLI ([[00-Amazon-Atlas]] → `cli/`) is built from the `READ` + `READ_FILE` allowlist
only. Excluded, by design and documented in each section's *Out of scope* table:
`READ_POST` (semantic reads over POST — the app may fire them, the CLI may not construct them),
`WRITE`, `EXPORT` (report enqueue), `UNKNOWN` (G1 denied), and `NOISE` (telemetry).
