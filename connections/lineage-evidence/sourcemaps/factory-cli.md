## 0. Headline

**Factory is roughly half SAP window, half genuinely-new data — and the split is clean enough
to name endpoint by endpoint.** Every command group that reads *stock, items, invoices,
orders, transfers, production orders, GL/tax config* is a **live pass-through read of SAP HANA**
(no cached copy anywhere — verified by the absence of any mirror table in the app's own
Postgres). Every command group that reads *cartons, scans, gate arrivals, weighbridge, QC
inspections, photos, approvals, drivers, dispatch plans, MES runs* is **native app data that
never reaches SAP**. In between sit five narrow **feeder** paths (material GRPO, service GRPO,
FG receipt, BOM request, production-run receipt) that post a *summary* document into SAP and
keep the rich detail behind.

Biggest surprise, and the highest-value finding: **the barcode/carton layer is enormous and
100% non-SAP.** 301,821 boxes, 791,851 box movements, 489,604 audit-log rows, 143,236 scans,
127,100 dispatch box-scans, 3,075 intercompany transfers — and the SAP write-back on both the
dispatch session and the intercompany transfer is **switched off**, verified live.

### The decisive negative: there is no SAP mirror in Postgres

I enumerated all 250+ tables in `factory_flow`. **There is no `oitm`, `oinv`, `oitw`, `oinm`,
`ordr`, `owor`, `ocrd`, `owhs` copy — not under any name.** The only SAP-derived *materialized*
table in the entire database is:

- `sales_planning_requirement_salesplanningrequirementrow` (288 rows) +
  `..._refreshrun` (its load log).

Everything else SAP-shaped that the API returns is therefore **assembled at request time from
HANA**. That is why I call those endpoints a live window rather than a stale mirror.

**Reclassification note — the "SAP-doc-num = 100%" trap.** Three tables have a SAP doc number on
*every* row, and that is evidence of the **opposite** of a feeder:

```sql
warehouse_bsttransfer            134 rows / 134 with sap_doc_num  (100%)
gate_core_salesdispatchgateout   801 rows / 801 with sap_doc_num  (100%)
gate_core_emptyvehiclegatein     817 rows /   0 with sap_doc_num  (0%)
```

A feeder starts null and gets filled on success (see `warehouse_bomrequest` 12/72,
`production_execution_productionrun` 14/86, `marketplace_marketplacedispatch` 50/2,116). A row
that is *born* with a SAP doc number was created **against** a document SAP already had. That is
exactly what `/gate-core/bst-outs/sap-transfers/` does — it lists **eligible existing SAP
transfers** for the operator to pick from. So: **the transfer/invoice is M; the gate event, the
box scans and the weighment hung off it are N.** BST is a reference, not a feeder. Empty-vehicle
gate-in, with 0/817, is unambiguously N.

**What gets dropped in the push (the reason the app is not redundant):** SAP receives accepted
quantity, price, tax code, GL account, warehouse and branch. It does **not** receive the QC
inspection that authorised it (chemist decision, QA-manager decision, remarks, 10,740 per-parameter
lab readings), the arrival-slip photos/CoA scans, the gate entry and truck/driver identity, the
weighbridge tare, the rejected quantity and its reason, the approval timestamps, or who approved it.
Same for service GRPO: SAP gets the freight amount; the bilty scan, transporter GSTIN, driver
licence, kanta weight and pipeline history stay here.

## 6. Smoking guns

1. **`barcode_dispatchsession.sap_update_status = 'NOT_CONFIGURED'` for all 185 sessions**, and
   `barcode_dispatchsapsynclog` is empty. The scan-to-ship dispatch never writes to SAP.
2. **`SELECT count(NULLIF(sap_doc_num,'')) FROM barcode_intercompanytransfer` → 0 out of 3,075.**
   Mart's entire stock-intake rail from Oil is invisible to SAP at carton level.
3. **`sales_planning_requirement_salesplanningrequirementrefreshrun`** — `procedure_name: "SALES
   PLANNING VS REQUIREMENT_WEEKLY"`, `source_schema: "JIVO_OIL_HANADB"`, `column_metadata` full of
   `hana_type_code`. Proves direct HANA SQL from Django, and is the only materialized SAP copy
   (last refreshed 2026-06-16 → 44 days stale).
4. **A live API error leaking the HANA driver**: `{"error": "(259, 'invalid table name: Could not
   find table/view PRODUCTION_RELEASE_OIL in schema JIVO_MART_HANADB')"}`.
5. **`grpo_grpoposting`: 232 of 265 postings carry a SAP doc number, latest 2026-07-28** — the
   material GRPO feeder is live and current (the Mart-only docs in this repo say "0 GRPOs ever
   posted", which is true for Mart and wrong for the group).
6. **`quality_control_materialtypesapitem` (135 rows)** — an explicit link table joining a native
   QC taxonomy to SAP `item_code`. Textbook "joined to SAP, not sourced from SAP".
7. **`production-execution sap-items` returns raw SAP casing** — `{"ItemCode","ItemName","UomCode"}` —
   the app didn't even bother renaming.
8. **`warehouse/wms/stock/movements` returns OINM semantics verbatim**: `reference` = DocNum,
   `doc_num` = TransNum, `created_by` = DocEntry.
9. **`product_identity.go` keys every factory item as
   `urn:jivo:factory:<COMPANY_CODE>:<SAP_SCHEMA>:<ITEM_CODE>`** — the factory item's identity *is*
   (company, HANA schema, SAP ItemCode).
10. **No SAP mirror table exists in 250+ `factory_flow` tables.** The negative is the finding.
