# EXIM — source map (M / F / N / X / U)

System dir: `/Users/damanpreetsingh/jivo-cli/exim`
Analyst run: 2026-07-30. EXIM API **reachable live**. SAP HANA **reachable live** via `hana-sql -env connections/hana-tunnel.env`.
SAP Service Layer (`sapb1`) unreachable from this workspace (no `SAPB1_*` config) — all SAP verification done by direct HANA SQL.

## Headline

EXIM is **two systems welded together**. Roughly a third of its read surface (22 of 65 commands: the whole
`sap-sync` family plus items/parties) is a **live, byte-exact SQL window onto SAP** — I matched row counts and
totals to the paisa against HANA. The other two thirds (`stock-status`, `tank`, `license`, plus the pricing and
rate modules) is **data SAP has never seen and has no table for**. There is **no EXIM→SAP write path at all**:
all 100 endpoints either read SAP or write EXIM's own Postgres, so the F bucket is empty. SAP document numbers
that appear on EXIM rows (`grpo_number`, `invoice_number`) are **hand-typed and demonstrably wrong**.

## Runtime & how the CLI authenticates

- CLI: Go + Cobra, generated by "CLI Printing Press". Binary `cli/exim-pp-cli/exim-pp-cli`; wrapper `./exim`
  mints/refreshes the JWT from the jivogpt root `.env`.
- Auth: `POST https://eximbe.jivo.in/account/login/` → `{access, refresh, permissions}`, then
  `Authorization: Bearer <access>`; refresh on 401. Login response embeds a per-user resource→ops permission map.
- Backend: Django-style REST at `https://eximbe.jivo.in`, trailing-slash routes. **65 read commands in 16 groups**
  (`tools-manifest.json`), 100 endpoints total in `endpoints.json` (35 write/sync, deliberately unwired).
- **Read-only caveat found:** `exim-pp-cli import <resource>` (`internal/cli/import.go:45`) builds `path := "/" + resource`
  and issues **POST per JSONL line**. `sync` is safe (local SQLite hydration, GETs only), but `import` is a real
  write path in a CLI documented as read-only. Not executed.

## Smoking guns (strongest proofs)

1. **`/sap-sync/open-ar/` is a raw SQL pass-through on the Beverages company.**
   Live: `./exim sap-sync get-open-ar` → **1168 rows, Σ Balance = ₹70,968,752.14**.
   HANA: `SELECT COUNT(*), SUM("DocTotal"-"PaidToDate") FROM JIVO_BEVERAGES_HANADB.OINV WHERE "DocStatus"='O' AND "CANCELED"='N'`
   → **1168 rows, 177421880353/2500 = ₹70,968,752.14**. Identical count, paisa-exact total. Invoice 626078350
   (CUSTA000844 ILAHI CO., ₹13,636, 2026-07-29) exists **only in JIVO_BEVERAGES_HANADB**, not Oil, not Mart.

2. **`/sap-sync/planned-months/` returns SAP `OFCT` rows verbatim.**
   The 7 keys returned (`AbsID, Code, Name, UserSign, StartDate, EndDate, FormView`) are *exactly*
   `SELECT COLUMN_NAME FROM SYS.TABLE_COLUMNS WHERE TABLE_NAME='OFCT'` — the full column list, in order.
   Live: EXIM 24 rows; HANA `JIVO_OIL_HANADB.OFCT` 24 rows; same AbsIDs (20,21,22,24,42,43…), same
   `"OIL Monthly Production Planning for the JULY Month 2026"`. Zero transformation, zero lag.
   (Beverages OFCT has only 6 rows — so this endpoint is definitively the Oil company.)

3. **`sync_logs` leaks the whole architecture** (Postgres error + `MSDASQL`/`HANADB112` linked-server error) —
   see datastore table above.

4. **Daily prices come from a Google Sheet, not SAP** — SPA string "Fetch today's commodity prices from the Google Sheet".

5. **EXIM's item namespace is a SAP look-alike that SAP has never seen.**
   Every `tank/items` code (`RMSESMT, RM0SESM, RM0RB02, RM00RBD, RM00CN, RM00CN2, RM00CPC, RM0CDRO, RM0EL, RM00P03, RMSEED, RM000SEEDS`,
   51 total, `created_by: admin@exim.com` / `lovepreet@exim.com`, Mar–Apr 2026) and every `stock-status` item code
   (`RM00SB, RM00MRD, RM0MKG, RM0CPCT 15KG, SBTIN15KG`, …) returns **zero rows** from `JIVO_OIL_HANADB.OITM`.
   Only the `RM00000xx` codes used by `items/rm`, `dc` and `sap-sync/open-pos` are real SAP codes.
   ⇒ tank + stock lots are keyed to a native master with **no FK into SAP**.

6. **SAP document references on EXIM rows are hand-keyed and wrong.**
   DC id 274 (vendor VENDA001531 BD EDIBLE OILS, grpo_date 2026-04-14) carries `grpo_number: "2026046615"`.
   In SAP, OPDN 2026046615 = **VENDA000808 RAM BHAJ SURESH KUMAR, ₹2,360**. The real BD Edible Oils GRPO on
   2026-04-14 is **2026046618 (₹67,31,723)**. Off by three, wrong vendor, wrong amount by 2850×.
   Likewise `stock-status/debit-entries` carries `grpo_number` values `'123','124','125'` — SAP OPDN DocNums
   run 125206500…2026076814, so those are pure noise.
   **This is the "joined ≠ sourced-from" trap made concrete: the reference field is native, unreliable EXIM data.**

7. **Nothing flows EXIM → SAP.** All 100 routes in `endpoints.json`: the four `sap_sync` triggers
   (`POST /sap_sync/rm/items/`, `POST /sap_sync/fg/items/`, `POST /sap_sync/party/{code}/`, `GET /sap_sync/open-grpos/`)
   all pull SAP→EXIM; every other write targets EXIM's own Postgres. **F bucket is empty.**

8. **Every mirrored master is stale and hand-cranked.** `sync_logs`: 342 runs, **`triggered_by` = "Manual" for all 342**.
   Latest per type — `PRD` (products) **2026-07-18**, `PRT` (parties) **2026-06-12** (7 weeks), `DMC` **2026-03-26** (4 months).
   No cron exists. The `sap-sync/*` GET family is unaffected (it is live pass-through, no sync-log rows).

## What I did NOT get to (stated plainly)

- **Backend source is not in this repo.** Everything is black-box: live API responses + minified SPA + HANA
  cross-checks. I never saw EXIM's Django views or its SQL. A background job could in principle push to SAP
  without an HTTP route; `sync_logs` (only PRT/PRD/DMC, all inbound-shaped, all `Manual`) argues against it,
  but that is inference, not proof. **F-bucket-is-empty confidence: 88.**
- `sap-sync get-vendor-balance-sheet`, `get-custa-balance-sheet`, `get-customer-ledger`, `get-vendor-ledger`,
  `get-customer-balance`, `get-finished-inventory` were **not pulled live** (two timed out, the ledgers need a
  `cardCode` I did not pick). Their rulings rest on response shape from `_raw/` + the verified siblings.
- `/sap_sync/open-grpos/` deliberately not called (workspace HARD-RULE flags it as possibly refresh-triggering).
- What `DMC` sync_type actually syncs (last run 2026-03-26, 390 records) — most likely domestic contracts from
  SAP POs, but unproven. This is the one thread that could upgrade DC from "88" to certain.
- The upstream of `/jivo-rate/fetch/` (see U above).
- Whether `rates/market-rate` is seeded from the same Google Sheet as `daily-price` (identical 12–13 commodity
  list and identical column names strongly suggest yes → that sub-entity would be **X**, not N).
- I did not check Mart/Beverages for tank/license tables — only `JIVO_OIL_HANADB`. Given EXIM demonstrably
  reads two companies, a tank table in another schema is unlikely but unchecked.
