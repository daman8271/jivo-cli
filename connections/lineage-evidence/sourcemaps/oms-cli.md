# Source map — oms-cli (JIVO OMS, `oms-pp-cli`)

Agent: oms-cli source-mapper. Date: 2026-07-30. Repo: `/Users/damanpreetsingh/jivo-cli/oms-cli`.

## Headline

**OMS is not a SAP window. It is the front half of the sales document chain: it *creates*
the order, then pushes it into SAP as a Sales Quotation — and it mirrors SAP master data
back down so its screens can render.** Roughly one third of the command surface (parties,
products, addresses, branches, live HANA reads) is a SAP mirror and is redundant with
`sapb1`/`hana-sql`. The other two thirds (the order object itself, approvals, party-product
rate assignments, schemes, app users, the invoice tracker, SKU images) exist **only** in
OMS and are permanently invisible to SAP.

## 3. THE CENTRAL FINDING — an OMS order becomes a SAP **Sales Quotation** (OQUT)

`order_management.sales_quotation_logs` columns:
`order_id, sap_doc_entry, sap_doc_num, status, request_data jsonb, response_data jsonb, error_message, created_at, completed_at`.

```
postsql query -d order_management "SELECT id, order_id, sap_doc_entry, sap_doc_num, status,
  left(request_data::text,900) FROM sales_quotation_logs WHERE status='SUCCESS' ORDER BY id DESC LIMIT 1"
```
→

### 3d. And SAP then converts the quotation into a real Sales Order

```sql
SELECT R."DocEntry", R."DocNum", R."CardCode", L."BaseEntry"
FROM JIVO_BEVERAGES_HANADB.RDR1 L JOIN JIVO_BEVERAGES_HANADB.ORDR R ON R."DocEntry"=L."DocEntry"
WHERE L."BaseType"=23 AND L."BaseEntry" IN (1159,1161)
```
→ ORDR 9398 / DocNum 1726078224 (from quotation 1159), ORDR 9400 / DocNum 1726078225 (from 1161).

Fleet-wide: `RDR1 WHERE BaseType=23` → 4,802 lines (Oil), 1,162 (Beverages).
`INV1 WHERE BaseType=23` → 0 in both, i.e. invoices are always raised from the *order*, never
straight off the quotation.

**Verdict on the question Daman actually asked:** an OMS order **does** become a SAP row —
but a `OQUT` quotation, not an `ORDR`, and the ORDR is SAP's own downstream conversion.
OMS **keeps its own copy** of the order (`orders` + `order_items` in Postgres) and reads back
from SAP only two things: the assigned `DocEntry`/`DocNum`, and the quotation's open/closed
status.

### 3e. The read-back is real and it is thin

Cached `quotation_status` vs live `OQUT.DocStatus`, 300 sampled quotations:

| OMS status | SAP DocStatus | rows |
|---|---|---|
| CLOSED | C | 286 (Oil) + 7 (Bev) |
| OPEN | O | 6 |
| OPEN | **C** | **1** ← stale read-back |

299/300 agreement. `order_management.orders` has **no** `quotation_status` column, so
`/api/orders/quotation-status/` must be querying SAP live at request time (inference,
~92 % confident). 550 of 1,457 cached quotations carry `quotation_status: "UNKNOWN"` —
i.e. the read-back had not run or failed for those.

### 3f. ⚠️ SAP keeps NO reference back to the OMS order

- `JIVO_BEVERAGES_HANADB.OQUT` and `ORDR` have **zero** `U_*` user fields
  (`SYS.TABLE_COLUMNS … COLUMN_NAME LIKE 'U\_%'` returns rows only for OCRD and OITM).
- On the two verified pushed quotations, `NumAtCard` is NULL and `Comments` is blank.
- No SAP user table `@…` in any of the three schemas relates to OMS orders, approvals or
  schemes (275 UDTs listed; grep for `oms|order|approv|scheme|track` → **0 hits**).

**Trap:** `JIVO_OIL_HANADB.OINV` *does* have columns literally named **`U_OMS_Order_No`**
(INTEGER) and **`U_OMS_REF`** (NVARCHAR 15). They are **not** foreign keys to this app.
4,598 of 30,477 Oil invoices have a non-null `U_OMS_Order_No`, and the values are
hand-typed junk that repeats: `4653` × 511, `4563` × 494, `1234` × 435, `123` × 178,
`1111` × 113. OMS order ids only reach ~2,038 and OMS order *numbers* are strings
(`ORD-20260718-0023`). `U_OMS_REF` is populated on exactly **1** row.
**Do not join OMS to SAP on `U_OMS_Order_No`.**

The only defensible OMS↔SAP joins are: `orders.id → sales_quotation_logs.sap_doc_entry →
OQUT.DocEntry` (plus company), and `card_code → OCRD.CardCode` / `item_code → OITM.ItemCode`.

## 4. The mirror half — "SAP logs" is an **import** job, not a push record

`sap logs` (`GET /api/sap/logs/`) → `order_management.sap_sync_logs`
(`sync_type, status, records_processed, records_created, records_updated, error_message,
started_at, completed_at, triggered_by`).

Cached production rows (CLI SQLite, `resource_type='sap'`):
```
PARTY_ADDRESS  SUCCESS  35434 processed / 23643 updated  triggered_by=manual  2026-07-16  508 s
PRODUCT        SUCCESS   4139 processed /  4139 updated  triggered_by=manual  2026-07-16   46 s
ALL            SUCCESS  42929 processed / 31139 updated  triggered_by=manual  2026-07-16  745 s
```
Backend rows (dev instance) show the same shape plus `BRANCH` and `PARTY` types.
`sync_type` values: `ALL`, `PARTY`, `PARTY_ADDRESS`, `PRODUCT`, `BRANCH`.

**So a "SAP log" = one run of SAP → OMS master-data replication.** It is the mirror's
audit trail, not evidence of a push. The push has its own log (`sales_quotation_logs`,
surfaced as `sap quotation-log <order-id>`).

**Lag:** `sap_sync_schedules` exists but is **empty (0 rows)**, and every `triggered_by`
value observed is `manual` / `verify` / `bulk-validation` — a human or a test harness.
There is a `django_apscheduler_djangojob` table but it too is empty. **Conclusion: the SAP
mirror is refreshed on demand, not on a cron.** The production cache showed the last full
`ALL` sync on **2026-07-16** with row `synced_at` timestamps of 2026-07-18 — i.e. staleness
of days, not minutes. Anything time-sensitive must go to HANA, not to `sap products`.

### The tracker, specifically

`tracker_stage` rows (live from the OMS backend):
```
1 Head Office In (entry, 2d) → 2 Bilty/GRPO (3d) → 3 Pre-Audit (3d) → 4 Data Entry (2d)
→ 5 SAP Approval (3d) → 9 JSAP Approval (3d) → 6 Save in SAP (2d) → 7 Payment (5d, terminal)
```
This is an **inbound / vendor** invoice movement workflow with `threshold_days`,
`days_spent`, `tracker_stuck_alert` (days_stuck vs threshold), `receiving_note`,
`hold_amount`, `debit_amount`, TDS/discount in `tracker_payment_detail`. Stage 6 is
literally *"Save in SAP"* — by construction the tracker records what happens **before** SAP
sees the document. SAP B1 holds none of it: no `@…` UDT matches, and the tracker parties
that do exist in SAP (`11 SEVEN GROUP` = `VENDA000807`) have no `OPCH` row carrying the
tracker's invoice numbers (5635/4141/423) in `NumAtCard`.

**Caveat:** production `tracker` returned 403 for the admin account used in the earlier
verification pass, and the 13 rows I could read are obvious test data (`invoice_number`
`123456`, `123`). The *schema* argument is strong; the *volume/production behaviour* is not
verified. Confidence 85.
