## HEADLINE

**ecom-cli is overwhelmingly NOT a SAP window.** 121 of its 138 commands (88%) read a
Postgres database that holds marketplace-originated and JIVO-app-originated data that
SAP B1 has never seen. Only the 17 `sap *` commands are SAP-lineage, and even they are a
thin read layer over SAP's own tables — plus two *stale local SAP snapshots*
(`oitm_master`, frozen since 2026-01-07; `sustain_dist`, last month = 2026-06) that are
the single most dangerous thing in this system, because they look like SAP and are not
current.

## 2. THE DECISIVE FINDING — ecom.jivo.in is backed by Postgres DB `test_supabase`

The database is confusingly named `test_supabase` (1400 MB, 118 public base tables +
28 views + 16 matviews, plus `master`/`reporting`/`staging`/`raw`/`quality`/`auth`/
`storage` schemas). It is **production**, not a test copy.

**Proof (live, cross-source row equality):**
The CLI's local cache holds a `platform` row captured from the live API:
```
{"id":37,"format":"AMAZON","type":"B2C","item_head":"COMMODITY","month":6,"year":2026,
 "targets":180000.0,"created_at":"2026-06-04T07:43:27.255263+00:00", ...}
```
Live query against Postgres:
```sql
SELECT * FROM month_targets WHERE id IN (34,35,36,37);
-- id=37 → format AMAZON, type B2C, item_head COMMODITY, month 6, year 2026,
--         targets 180000.00, created_at 2026-06-04 13:13:27.255263+05:30
```
`created_at` matches **to the microsecond** (07:43:27.255263Z = 13:13:27.255263+05:30).
`updated_at` and `done_ltrs` have since MOVED FORWARD in Postgres (cache: 2026-06-26 /
101 987 L → Postgres: 2026-07-27 / 129 139 L), which is exactly the signature of a live
production table whose cached snapshot is old. Confidence this is the ecom backend: **97%**.

**Freshness check (live):** `reporting."Amazon PO"` max `order_date` = 2026-07-29,
`swiggySec` max `ORDERED_DATE` = 2026-07-28, `zepto_inventory` max `inventory_date` =
2026-07-29, `raw.upload_file` latest upload = 2026-07-29 14:59, matview refresh
(`matview_refresh_state`) = 2026-07-29 16:24. The DB is current to yesterday.

**Not the backend:** the same cluster has a `jivo_ecom` DB (55 MB, 17 tables) with the
same *shape* (amazon_po, appointment, products, distributors, shipments, sec_sales_master_*)
but `distributors`=0, `shipments`=0 rows. That is an **earlier / abandoned iteration** of
the app, not what `ecom.jivo.in` serves today. Do not read it as production.

## 3. Does the Postgres backend contain SAP data? — three hard negatives

Checked live against `test_supabase`:

1. **No SAP document tables at all.** No `oinv`, `inv1`, `ordr`, `rdr1`, `ocrd`, `opor`,
   `oitw`, `oitb`, `ojdt` — nothing. `search('cardcode')` → **0 hits**.
   `search('docentry')` → exactly **one** hit: `oitm_master.docentry`.
2. **No federation.** `SELECT extname FROM pg_extension` → `pg_stat_statements, pgcrypto,
   plpgsql, uuid-ossp`. **No `postgres_fdw`, no `oracle_fdw`, no foreign tables**
   (`pg_class WHERE relkind='f'` → 0 rows). There is no SQL-level bridge from this
   Postgres to SAP HANA.
3. **No SAP table feeds any analytics view.** I dumped the full view/matview dependency
   graph (`pg_depend` → `pg_rewrite`). All 43 views/matviews in `public` resolve to
   marketplace tables + `master_sheet` + `monthly_landing_rate` + `status_mapping` +
   `city_state_mapping`. **Not one view references `oitm_master` or any SAP object.**

**Conclusion:** the `/api/sap/*` routes cannot be served from Postgres for invoices,
orders, distributors or stock — that data is simply not there. They must open a
connection to SAP from the FastAPI/Django backend process itself. This is consistent
with everything else the surface says (see §4).

## 5. SMOKING GUNS — the two stale SAP copies inside the ecom DB

### 5a. `public.oitm_master` — a frozen SAP OITM snapshot (M, STALE ~204 days)
Columns are literally SAP OITM columns: `docentry, itemcode, itemname, itmsgrpcod,
u_unit, u_sku, u_sub_group, u_islitre, u_gross_weight, u_mrp, u_shelflife, prchseitem,
sellitem, onhand, lastpurdat`. The `u_*` prefix is SAP B1's user-field convention —
this is a copy of JIVO's own OITM UDFs.

```sql
SELECT count(*), min(created_at), max(created_at), max(lastpurdat) FROM oitm_master;
-- 2014 rows | 2026-01-07 12:19:40.738793+05:30 | 2026-01-07 12:19:42.357158+05:30 | 2026-01-07
```
**All 2 014 rows were written inside a 1.6-second window on 2026-01-07 and never touched
again.** There is no refresh job. Its `onhand` column (e.g. FG0000379 MUSTARD KACHI GHANI
1 LTR = 30 832) is stock as of 7 Jan 2026 — **~6.7 months out of date today**. No view
references it, so it is not silently poisoning the dashboards, but anything that reads it
directly is reading January.

### 5b. `public.sustain_dist` — SAP primary offtake, monthly, 2 months behind (M, STALE)
`sap_code, quantity, rate, value, date` — 42 rows, `sap_code` values are SAP ItemCodes
(`FG0000004`, `FG0000005`, …), `max(date) = 2026-06-01`. This is JIVO's primary sales
(SAP-invoiced) to SUSTAINQUEST (the e-com selling entity), aggregated per item per month
and pushed into the ecom DB. SAP holds the source; this is a lagging aggregate copy.

### 5c. `warehouse_inventory` / `distributor_inventory` / `distributors` — dormant sync caches
`warehouse_inventory` (110 rows) and `distributor_inventory` (0 rows) both carry a
`last_synced_at` column — the classic ingest-cache tell.
```sql
SELECT min(last_synced_at), max(last_synced_at) FROM warehouse_inventory;
-- 2026-05-17 00:22:10 | 2026-05-18 23:52:18
```
**The sync stopped on 2026-05-18 and has not run in 73 days.** `distributors` has 1 row,
`distributor_inventory` 0, `in_transit_inventory` 0. This whole sub-module is effectively
dead. If any `sap inventory-*` endpoint reads these, it is serving May data as "SAP".

## 6. THE JOIN-KEY TRAP — SAP codes that are NOT SAP-sourced rows

`search(test_supabase, 'sap')` returns exactly these columns:

| Table | SAP-shaped column | What the row actually is |
|---|---|---|
| `public.master_sheet` | `sku_sap_code`, `sku_sap_name` | JIVO's **own uploaded SKU bridge**: `format_sku_code` (marketplace SKU) ↔ SAP code, plus `packaging_cost`, `tax_rate`, `case_pack`, `per_unit_value`, `item_head`. Origin = an Excel file uploaded by the e-com team. |
| `master.product_master` | `sap_sku_code`, `sap_sku_name` | app product master carrying `asin`, `merchant_sku`, `distributor_margin`, `core_fresh_now` — none of which exist in SAP |
| `reporting."Amazon PO"` | `sap_sku_code`, `sap_sku_name` | an **Amazon Vendor Central PO**, enriched with the SAP code via `master_sheet` |
| `public.sustain_dist` | `sap_code` | genuinely SAP-sourced (see 5b) — the one exception |

`master_sheet` is the hinge of the entire app: 30 of the 43 analytics views join through
it. It is the reason marketplace rows carry SAP codes. **A `sap_sku_code` on an Amazon PO
row does not make that row SAP data** — the PO was raised by Amazon, uploaded as a file,
and decorated with a SAP code afterwards. This is the single most likely place for this
whole lineage analysis to go wrong.

## 8. Things SAP B1 categorically does not hold (verified by column inspection)

- **`public.amazon_mp` (8 597 rows)** — Amazon Marketplace **consumer-level GST invoices**:
  `invoice_number, buyer_name, ship_to_city/state/postal_code, irn_number, irn_filing_status,
  tcs_cgst_amount, item_promo_discount, gift_wrap_amount, fulfillment_channel`. SAP sees a
  settlement/B2B document from Amazon at best; it never sees the end-consumer invoice.
- **`public.swiggySec` (634 208 rows)** — Swiggy Instamart **dark-store-level** sell-out:
  `STORE_ID, AREA_NAME, CITY, L1/L2/L3_CATEGORY, BASE_MRP, UNITS_SOLD, GMV`. SAP has no
  concept of which Swiggy store sold a bottle.
- **`public.meta_data` (354 rows)** — despite the name, this is **Meta/Facebook Ads**:
  `campaign_name, campaign_status, amount_spent, impressions, reach, unique_clicks,
  cost_per_click, cost_per_1000_reach`. (`platform meta` = Meta ads, not "metadata".)
- **`reporting.price` (96 rows)** — **competitor price scraping** off listing pages:
  `url, url_price, stock_status, seller, rk_price, jm_price, svd_price, bau_price, art_price`.
- **`public.sp_shipments` / `shipments` / `truck_dispatches`** — `driver_name, driver_phone,
  vehicle_number, load_percentage, auto_planned, approved_by, rejection_reason, created_by`.
  Approval trail + rejected records + logistics execution state.
- **`public.sp_audit_log`** — `changed_by, change_type, old_asin/new_asin, old_qty/new_qty,
  reason, reason_note`. A full edit/approval trail.
- **`public.accounts_inventorydohnotification` (3 785 rows)** — app-generated alerts with
  `severity, threshold, is_read, resolved_at, first_seen_at`. Workflow state, not accounting.
- **`raw.upload_file` + `quality.validation_error` (13 226 rows)** — the ingest audit trail:
  `file_hash, uploaded_by, row_count, error_count, warning_count, stored_file_path`.
- **`public.blinkit_brandfund` / `swiggy_brandfund` / `zepto_brandfund`, `amazon_coupon`** —
  trade-spend at campaign/SKU/city granularity. SAP may hold the net credit note; it does
  not hold the campaign breakdown.

## 9. Feeder (F) check — does anything here get pushed INTO SAP?

**No evidence of any push path from ecom → SAP.** Every one of the 138 commands is a GET;
the app has no SAP write route exposed. `sustain_dist` and `oitm_master` both flow
SAP → ecom, not the reverse. I found **no** table with a `posted_to_sap`, `sap_doc_entry`,
`sync_status`, or similar push marker. I am therefore recording **zero F entities** for
this system — with the caveat that a server-side job invisible to both the CLI surface
and the Postgres schema could exist. Confidence no-F: 80%.

## 10. Coverage gaps — stated plainly

1. **No live API rows.** Token 401. Everything about response *shape* is from code/spec;
   everything about *content* is from the Postgres backend and the stale local cache.
2. **No live SAP.** HANA tunnel hangs; Service Layer unconfigured. I could not verify that
   OINV/ORDR/OCRD are populated, and could not compare a `sap sales-analysis` total against
   SAP. All SAP-side claims are code/schema-grade, not live.
3. **Backend source not read.** The FastAPI/Django code behind `ecom.jivo.in` is on the app
   server and is not in this repo. The live-proxy-vs-local-cache call for `/api/sap/*` is
   therefore an inference from three hard negatives, not a code read. **This is the single
   weakest link in my analysis** and the thing worth 20 minutes of someone else's time.
4. **Company/database scope of the SAP layer is unknown** (§4).
5. `product_batches` (78 rows, `batch_number/manufacture_date/expiry_date`) — SAP B1 *does*
   have batch management (OBTN with ExpDate). I could not check whether these batch numbers
   exist in SAP. Marked **U**.
6. I did not exhaustively open all 43 platform subcommands individually; I mapped them by
   endpoint family to their backing tables via the view dependency graph, which covers every
   group but not every leaf.
