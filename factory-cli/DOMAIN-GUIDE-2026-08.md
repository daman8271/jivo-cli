# Jivo Factory — what each domain actually means

Written from a live study of the factory API on 2026-08-03: every domain was
read out of the app's own frontend bundle and checked against live responses,
then put through an adversarial review that tried to refute it.

**Read the gotchas.** They are the difference between a command that returns
a number and a command that returns the *right* number. Several were found
only because a reviewer tried to prove the first answer wrong.

## Attendance, security checks & weighbridge

*5 read commands · 6 write endpoints excluded*

This group covers three small, separate parts of the gate operation. (1) **Attendance** is the manual attendance register — the app's own subtitle is "Manual attendance register — used when the punching machine is unavailable". A gate operator picks an employee, marks IN or OUT, and must attach a photo as proof of presence; the dashboard then rolls the day up per employee into First In / Last Out / number of marks, and can export a date range to Excel. It is a fallback register, never the payroll source of truth. (2) **Security checks** are the guard's inspection of an incoming raw-material vehicle at gate-in step 1: vehicle condition, tyre condition, fire extinguisher present, seal number before/after, alcohol test, who inspected, remarks. Each check is saved against a gate entry and later finalised ("submitted") by a separate action. (3) **Weighment** is the weighbridge record for the same gate entry: gross weight, tare weight, net weight, weighbridge ticket number, and the two weighing timestamps. Read-side, all three are thin: attendance has three list/export endpoints, and security and weighment each expose exactly one per-gate-entry detail read. Everything else in these three path segments is a write and is excluded. Practically, the attendance module is deployed but completely unused — zero employees and zero records in all three companies — while security checks and weighment carry real daily production data in all three.

### Traps

1. TRAILING SLASH — the single biggest trap. The app's own frozen ENDPOINTS constant emits `/security-checks/gate-entries/${e}/security/view` and `/weighment/gate-entries/${e}/weighment/view` WITHOUT a trailing slash and relies on Django APPEND_SLASH. I measured it: unslashed = HTTP 301 with an empty body, slashed = HTTP 200 with the record. If a generated client copies the path from HARVEST/the bundle and does not follow redirects, both endpoints silently return nothing. Canonical paths must carry the trailing slash.

2. ATTENDANCE IS DEPLOYED BUT COMPLETELY EMPTY. Zero employees and zero records in all three companies — verified live over the full 2026-01-01..2026-08-03 range, plus unfiltered calls. The export returns a 5137-byte header-row-only workbook, byte-identical in all three companies. Three commands that always return nothing look broken; the description must say the register is currently unused, or an operator will file a bug against the CLI.

3. THE {id} IS THE GATE/VEHICLE ENTRY ID, NOT THE RECORD ID. `/security-checks/gate-entries/2832/security/view/` takes vehicle_entries.id = 2832 and returns security-check id 1032. The one exception is the excluded write `/security-checks/security/{id}/submit/`, which takes the security-check id instead. Two different keys, near-identical URLs. Source real ids from `/vehicle-management/vehicle-entries/?entry_type=RAW_MATERIAL&from_date=..&to_date=..` — and note that endpoint 400s with `{"detail":"from_date query parameter is required"}` if you omit the dates.

4. THESE ARE RAW-MATERIAL-ONLY RECORDS. Security check and weighment belong to the raw-material gate-in flow. In practice every RM gate entry gets a security-check row at step 1 — OIL entries 2792..2837 map to check ids 1023..1034 in lockstep — but weighment is frequently absent: 5 of the 12 OIL entries I sampled had `weighment: null`. Asking for a weighment on a SALES_DISPATCH or EMPTY_VEHICLE entry is meaningless (and is exactly the probe I refused to run).

5. NET WEIGHT IS A STORED COLUMN, NOT A COMPUTED ONE, AND IT LIES. Entry 2612 (BEVERAGES): gross "12345.000", tare null, net "0.000" — net ≠ gross − tare. The UI does not trust it either; RequiredWeighmentForm recomputes net client-side as max(0, gross − tare) to 3 dp and renders it read-only. Never report net_weight as authoritative without showing gross and tare.

6. TWO SERIALIZERS DISAGREE ON THE SAME ROW. For MART entry 466 / weighment id 68, `/gate-core/raw-material-gate-entry/466/` reports gross/tare/net as `null`, while `/weighment/gate-entries/466/weighment/view/` reports `"0.000"` for all three. Do not read 0.000 as "the truck weighed zero" — it can mean "never weighed".

7. WEIGHTS ARE KILOGRAMS, AS DECIMAL STRINGS. "56610.000" is 56.61 MT, not 56,610 tonnes. Convert to tonnes for operators (JIVO house style) and parse the string, don't assume a number type.

8. THE ALCOHOL TEST IS TWO BOOLEANS BEHIND A FOUR-STATE DROPDOWN. The UI select offers Not Required / Required / Passed / Failed, stored as `alcohol_test_done` + `alcohol_test_passed`. `alcohol_test_passed: true` with `alcohol_test_done: false` means NOT TESTED, not "passed" — and that is the common case (OIL 1032 and BEV 1033 both look like this). Reporting it as a pass is a safety-compliance misstatement.

9. `is_submitted: false` MEANS DRAFT. The guard saved the check but never finalised it (finalisation is the excluded POST .../submit/). Verified: OIL 1032 and BEV 1033 are false; MART 448 is true. Do not count unsubmitted checks as completed security clearances.

10. ATTENDANCE FILTER TYPES. `department` is a department ID (int) from `/accounts/departments/` — 1=IT, 2=Ecom, 3=Account, 4=Store, 5=Others, 6=Mess, 7=Live Smoke Dept, 8=production, 9=production(oil), 10=production(beverages), 11=store RM-PM, 12=Warehouse Beverage, 13=Warehouse Gupta — never a name. `employee` is an employee ID, not employee_code. `is_active` must be the lowercase string `true`/`false` (the client does String(bool)). `direction` is the DRF choice `IN` | `OUT`.

11. `direction` WORKS ON THE LIST EVEN THOUGH THE UI NEVER SENDS IT. The React client's getRecords omits `direction`; only exportRecords sends it. But the server's own export docstring says "the same filters as the list endpoint (employee, department, direction)", and `?direction=IN` returns 200 live. Declaring it is correct; omitting it loses a real filter.

12. THE EXPORT IS BINARY, NOT JSON. `/attendance/records/export/` returns an xlsx with a Content-Disposition filename. A client that JSON-decodes every 200 will fail on it; it needs an --output FILE flag.

13. NO PAGINATION ANYWHERE IN THIS GROUP. All three attendance endpoints return a bare JSON array (or a file); both detail views return a bare JSON object. No results/count/page/page_size/total_pages/next/previous on any of the five. A --page/--page-size flag here would be dead.

14. NO 400 ENVELOPE OBSERVED IN THIS GROUP. None of the five endpoints has a required query param, so I never triggered an error body from them. The one 400 I hit while sourcing ids came from a neighbouring endpoint and used the `{"detail": "..."}` style — do not assume that is this group's contract.

15. BUSINESS FRAMING. Attendance is explicitly the manual fallback register ("used when the punching machine is unavailable"), and every mark requires a photo as proof of presence. It is not, and should never be presented as, the payroll source of truth.

### Gone or broken since July

- Corollary worth flagging to the assembler: because there is no July precedent, there is also no prior operator usage to fall back on — the attendance commands in particular will be shipping into a module that has never held a single row.

### Confidence & open questions

VERIFIED LIVE BY ME (2026-08-03, serial requests, JIVO_MART / JIVO_OIL / JIVO_BEVERAGES):
- All five GET endpoints returned HTTP 200. Method sets came from live `OPTIONS` Allow headers, not from the bundle's is_mutation flag: /attendance/employees/ and /attendance/records/ = "GET, POST, HEAD, OPTIONS" (dual-use, GET published only); /attendance/records/export/, both /view/ endpoints = "GET, HEAD, OPTIONS".
- The 301-vs-200 trailing-slash behaviour on both /view/ endpoints — measured, both paths, both variants.
- Attendance emptiness — [] in all three companies, including a 2026-01-01..2026-08-03 sweep and unfiltered calls; export = 5137 bytes, header row only.
- Every response shape quoted for the two /view/ endpoints is a verbatim live payload, on rows that already existed (OIL 2832/2817, BEV 2836/2612, MART 466), chosen specifically so a get_or_create could not fire.
- Filter acceptance: date, date_from, date_to, department=8, direction=IN, is_active=true, search — all 200, no 400.
- Export column headers — read out of the returned .xlsx workbook itself.
- The safe alternative /gate-core/raw-material-gate-entry/{id}/ — OPTIONS name "Raw Material Gate Entry Full", docstring "(read-only)", Allow GET/HEAD/OPTIONS, verified returning nested security_check + weighment in all three companies.

INFERRED, NOT VERIFIED:
- Attendance element field lists. Both tables are empty everywhere, so I never saw a real row. The fields come from the server's own DRF OPTIONS serializer metadata (authoritative for names, types, required-ness and the IN/OUT choices) plus the AttendanceDashboard render code. High confidence on names and types, but I have not seen a populated record.
- Whether the `search` filter on /attendance/employees/ covers name + code + department server-side. I only confirmed it does not 400; the field list is the UI's client-side filter.
- Whether the Company-Code header is even consulted by the two /view/ endpoints. Gate-entry ids are globally unique across companies (2832=OIL, 2836=BEV, 466=MART coexist), so the header may be inert there. I only ever read each entry under its own company — testing a cross-company read would have been a probe against an entry with no row for that scope, which is the forbidden experiment.

NOT DETERMINED — and this is the one open item that matters:
Whether the two /view/ endpoints are `get_or_create`. I could not clear them without running exactly the probe that created six junk marketplace rows on 2026-08-03: reading a gate entry that has NO security-check / NO weighment row. I refused. So both carry side_effect_risk = suspected-get-or-create and, per the rule, MUST NOT ship as commands yet — even though every piece of zero-risk evidence I could gather (GET-only Allow, no DRF `actions` block, server docstrings that say "Get ... details", unchanged updated_at after read) points at a plain read. Confidence they are safe: roughly 85%, and what is stopping it from being certain is that the Allow header genuinely does not discriminate — the marketplace get_or_create also lived inside a GET handler. A single look at the Django view source, or one deliberate probe against an entry known to have no row, settles it either way. Until then the assembler should ship the zero-risk substitute /gate-core/raw-material-gate-entry/{id}/, which I verified returns the same two records nested and is documented read-only by the server itself.

Endpoint-set completeness: high. A full literal sweep of main.js and all 575 chunks for `/attendance/`, `/security-checks/` and `/weighment/` returned exactly ten API paths (plus two React route strings, /gate/attendance/employees and /gate/attendance/new, which are not API paths). Five GET, five write-only. HARVEST.json's twelve entries for this group are the same ten, counting both slash variants of the two /view/ paths twice.

## Barcode traceability

*35 read commands · 37 write endpoints excluded*

This is JIVO's carton-level traceability system — the barcode that gets stuck on every box coming off a filling line, and everything that happens to that box afterwards. A production run generates BOX barcodes (BOX-YYYYMMDD-LL-NNNN, LL = production line, RP = repack); boxes get stacked onto PALLET barcodes (PLT-YYYYMMDD-XX-NNN); pallets and boxes get moved between warehouses/bins, split, cleared, dismantled or voided. When a box is opened and its bottles are not all used, the remainder is booked as "loose stock" with a reason (REPACK/SAMPLE/DAMAGED/RETURN/OTHER) and can later be repacked into a new RP box. Dispatch works off a SAP bill: an operator pulls up an AR invoice/delivery, opens a dispatch session, scans pallets and boxes against the bill lines, and the session tracks expected vs scanned vs pending quantity, rejected scans with a reason code, and a SAP sync status. Intercompany transfers move physical stock between the three JIVO companies by scanning the barcodes (JIVO_OIL -> JIVO_MART is by far the busiest route, ~3,135 transfers), and the traceability screen follows one barcode across companies. There is also a label print/reprint audit trail (every label print is logged with printer name and reprint reason), a pallet "verify request" queue for disputed pallet counts, and a read-only SAP OITM item lookup used when generating labels. Everything here is live in all three companies; only /barcode/production-release-oil/ is JIVO_OIL-only, because it reads a HANA view that exists only in JIVO_OIL_HANADB.

### Traps

1. PAGINATION IS OPT-IN, AND OMITTING IT SILENTLY TRUNCATES. Thirteen barcode list endpoints return a BARE ARRAY CAPPED AT 500 ROWS when you send no page/page_size, and a full DRF envelope {results,count,page,page_size,total_pages,next,previous} the moment you send either. GET /barcode/boxes/ with no params returns 500 rows; count is 100,314 in MART and 224,549 in OIL. A generated command without a page flag would hand an operator 0.2% of the boxes and look like it worked. Affected: boxes, pallets, loose, print/history, scan/history, voids/boxes, voids/pallets, verify-requests, intercompany/transfers, dispatch/sessions, dispatch/sessions/active|completed|closed. The SPA hides this — barcode.api normalises both shapes with a helper that fabricates a fake envelope around a bare array (count = the truncated length), so the UI cheerfully shows "500" as if it were the total.

2. THE OTHER SIX ENDPOINTS IGNORE PAGE PARAMS AND CAP HARD. /barcode/dispatch/reports/boxes/ and /pallets/ return exactly 1000 rows and no more — verified by filtering to material_code=FG0000384, which still returned exactly 1000. /rejected-scans/ hits the same 1000 in OIL. /barcode/items/oitm/ takes `limit` (default 100) but the server caps it at 200 — limit=201 and limit=1000 both return 200 in MART and OIL, while BEVERAGES returns its true 98. /barcode/production-release-oil/ takes `limit`, default 100. Do NOT emit --page/--page-size on any of these; emit the filters instead, because filters are the only way to see past the cap.

3. /barcode/dispatch/sessions/from-bill/ MUST NOT BECOME A COMMAND. It is the POST that CREATES a dispatch session from a SAP bill. Its GET happens to return 200 — but the body is byte-identical to /barcode/dispatch/sessions/ (same count, 57 on MART, 128 on OIL); it is a router fall-through, not a real read. Publishing it would ship a duplicate command whose name promises a bill lookup, sitting on the URL of a session-creating POST. The current spec.yaml v0.3 DOES publish it as `dispatch-sessions-from-bill` — remove it.

4. THE COMPANY MATRIX IS WRONG FOR THREE OIL ROWS. company-matrix-2026-08.tsv records HTTP 0 for JIVO_OIL on /barcode/dispatch/sessions/, /sessions/active/ and /sessions/from-bill/. That is a client TIMEOUT on a huge unpaginated payload (OIL's completed-sessions list alone is 7.8 MB), not a routing failure. Re-verified live 2026-08-03 with ?page=1&page_size=1: all three return 200, count 128 / 84 / 128. JIVO_OIL is the BUSIEST dispatch company, not a dead one.

5. COMPANY SCOPING IS ENFORCED, AND IDS ARE GLOBAL. Box and pallet ids come from one sequence shared across all three companies (MART box 325836 and OIL box 325912 were both created today), but rows are filtered by the Company-Code header. Ask for a MART box with Company-Code JIVO_OIL and you get 404 {"error":"Box 325836 not found."} — not a permission error, just the wrong company. Every id-taking command must carry --company, and "not found" must be reported as "not found IN THIS COMPANY".

6. TWO ENDPOINTS RETURN 200 FOR "NOTHING FOUND". /barcode/lookup/{barcode}/ answers 200 {"entity_type":"UNKNOWN","entity_id":null,"entity_data":null} for a barcode it cannot resolve (verified by querying a MART barcode against JIVO_OIL). /barcode/intercompany/trace/?search=X answers 200 with every field blank and history [] for a barcode that has simply never crossed companies. A CLI that checks only the status code will report success and print an empty box. Check entity_type and history length.

7. `search` IS SILENTLY IGNORED ON scan-history. GET /barcode/scan/history/?search=BOX-20260727-XX-6411 returns count 80,733 — the unfiltered total. Unknown params are dropped, not rejected. scan_type, entity_type and scan_result DO filter (verified: 80,711 / 80,402 / 72,495). Do not expose --search on scan-history; do expose it on boxes, pallets, voids/*, intercompany/transfers and dispatch/sessions where it is verified working.

8. FOUR ERROR ENVELOPES EXIST API-WIDE; BARCODE USES TWO. Barcode emits {"error": "..."} (e.g. "Search value is required.", "item_code is required.", "Box 325836 not found.") and {"code":"...","error":"..."} (e.g. {"code":"SESSION_NOT_FOUND","error":"Dispatch session not found."}). It does NOT use the DRF {"field": ["..."]} or {"detail": "..."} styles. A handler that only reads `detail` will print nothing useful here.

9. THE 503 ON production-release-oil LEAKS A RAW HANA ERROR. MART and BEVERAGES return {"error":"(259, 'invalid table name:  Could not find table/view PRODUCTION_RELEASE_OIL in schema JIVO_MART_HANADB: line 20 col 37 (at pos 554)')"}. Translate it to "this report exists only for JIVO_OIL"; never surface the schema name and SQL position to an operator.

10. TWO HISTORY ENDPOINTS ARE DEAD. /barcode/boxes/{id}/history/ and /barcode/pallets/{id}/history/ return 200 [] for every id tested (3 boxes across 2 companies including one with a SHIP scan and one voided; 2 pallets) — while the corresponding DETAIL endpoints return a populated `movements` array for the same objects. Route "history" questions to `box` / `pallet`, not to these.

11. FIELD NAMES ARE INCONSISTENT BETWEEN BOXES AND PALLETS. On a box, `box_barcode` is the string and `id` is the key. On a pallet, `pallet_id` is the STRING barcode (PLT-...) and `id` is the numeric key. In the dispatch reports the same things are called `pallet_barcode` and `material_code`. Do not let a generator infer that pallet_id is a number.

12. STATUS ENUMS FROM THE UI DROPDOWNS ARE INCOMPLETE. Boxes: ACTIVE, PARTIAL, DISMANTLED, VOID (dropdown, matches data). Pallets: dropdown offers ACTIVE, CLEARED, SPLIT, VOID but live rows also carry PARTIAL and DISPATCHED. Dispatch sessions: the reports dropdown offers ACTIVE, PARTIAL, COMPLETED, CLOSED, CANCELLED, but DRAFT appears in live rows. Loose: ACTIVE, REPACKED, CONSUMED with reason REPACK, SAMPLE, DAMAGED, RETURN, OTHER. Verify requests: OPEN, IN_PROGRESS, RESOLVED, CANCELLED. Print: label_type BOX|PALLET, print_type ORIGINAL|REPRINT. Treat all of these as observed-values-only and pass the filter through rather than validating against a closed list — and never sweep an enum against the live API to discover more.

13. BARCODE DISPATCH DOES NOT POST TO SAP TODAY. Every dispatch session in MART and OIL carries sap_sync_status NOT_CONFIGURED with sap_sync_error "SAP sync is disabled for barcode dispatch." Intercompany transfers show sap_enabled false. So barcode dispatch quantities are NOT reflected in SAP — an operator comparing this to SAP delivery quantities will find gaps, and that is expected, not a bug. Say so in the command help.

14. WRITES OUTNUMBER READS IN THIS DOMAIN. Of the 72 barcode leaves in the app's own ENDPOINTS constant, 35 are GET-readable and 37 are write-only or write-first. Four published GET paths accept a write verb on the SAME URL: /barcode/dispatch/settings/ (PATCH), /barcode/pallets/{id}/ (DELETE), /barcode/intercompany/transfers/ (POST), /barcode/verify-requests/ (POST). Any method filter must key on the methods array, never on an is_mutation flag.

### Confidence & open questions

VERIFIED LIVE (high confidence, 2026-08-03, ~70 serial GETs of my own on top of the bundled probe files): all 35 published endpoints returned 200 with the shapes stated; the 500-row default cap (boxes 500 of 100,314); the opt-in DRF envelope on 13 endpoints; the 1000-row hard cap on the two box/pallet dispatch reports (proved by filtering and still getting exactly 1000); the 200 cap on items/oitm limit (proved across two companies); `search` being ignored on scan-history but honoured on boxes/pallets/voids/transfers/sessions; the verbatim 400 bodies for trace and oitm/detail; the verbatim 503 HANA body for production-release-oil; cross-company 404 on box and session details; lookup returning 200/UNKNOWN for an unresolvable barcode; every filter marked "verified live" in the params (status, warehouse, unpalletized, reason, label_type, print_type, material_code, box_barcode, pallet_barcode, customer, from_date/to_date, scan_type, entity_type, scan_result); and the correction that JIVO_OIL dispatch sessions are alive (128) rather than the matrix's HTTP 0.

INFERRED, NOT VERIFIED: (a) that /barcode/dispatch/sessions/active|completed|closed/ accept the same status/search filters as the base list — same viewset, but I only verified the filters on the base path; (b) the `search` param on loose and print/history (read out of the UI components, not separately counted); (c) that /barcode/dispatch/reports/ itself has a 1000-row cap — its largest company only has 128 rows, so I never reached one; (d) the full parameter surface of /barcode/production-release-oil/ and /barcode/scan/history/, neither of which has a call site in the SPA bundle, so the params I list came from probing rather than the UI and there may be more.

WHAT I COULD NOT DETERMINE: (1) Whether /barcode/dispatch/settings/ is backed by a get_or_create on company. I marked it side_effect_risk "none" and I want that judgement visible rather than buried — the reasoning is that it accepts NO lookup key, returns no id, and all three companies' rows pre-date every probe in this survey (created_at 2026-05-30 / 2026-06-01 / 2026-06-16), so nothing in this work created one; the only residual exposure is a hypothetical fourth company code, which I did not and will not test because that is exactly the sweep that created the six junk marketplace rows. If the reviewer wants zero exposure, drop it — it is one settings object. (2) Whether the box/pallet history endpoints are genuinely broken or just empty for the five objects I sampled; I could not reach a case that returned data. (3) The complete enum for scan_type, rejection_code and dispatch session status — I refused to enumerate values against the live API and only report what appeared in real payloads or the bundle. (4) Whether the 200-row ceiling on items/oitm is a server cap or coincidentally the exact item count in two companies; two different companies both stopping at exactly 200 while a third returns 98 makes a cap much the likelier reading, but I did not confirm it against the backend. (5) MART and OIL scan-history totals are oddly close (80,733 vs 80,681) despite very different box populations — I confirmed the rows themselves are company-correct (each company's top row references its own boxes) and BEVERAGES is properly small at 108, so scoping works; I have no explanation for the near-match and did not chase it.

NOTHING LOST SINCE JULY: all 15 barcode paths in research/get200.txt still return 200 today. Six paths are NEW and absent from the July baseline — /barcode/dispatch/sessions/, /barcode/intercompany/transfers/, /barcode/production-release-oil/, /barcode/verify-requests/, /barcode/voids/boxes/, /barcode/voids/pallets/ — plus 14 detail/sub-resource endpoints the July sweep never probed. The only regression-shaped things are the two always-empty history endpoints, and I cannot prove they ever worked.

## Bottle blowing

*14 read commands · 15 write endpoints excluded*

The blowing module tracks JIVO's own PET bottle-making: a blow-moulding machine heats plastic "preforms" (test-tube-shaped blanks bought from a supplier) and blows them into finished bottles. Operators book a **run** (one machine + one preform size for one day), request the preforms from the warehouse, then start/stop production and log breakdowns against it; the app costs the run automatically and shows ₹ per bottle. The masters behind that are **preform-specs** (a bottle size: make, preform gram weight, preforms per box, preform rate per bottle, SAP item code, and optional standards to measure against), **machines** (blow moulders, with SAP warehouse and depreciation per day), **rate-configs** (the older dated rate sheet: operator/labour/electricity/scrap/packing per day or per bottle) and **cost-rates** (the newer Cost Master: one rate per cost category — OPERATOR, LABOUR, ELECTRICITY_MACHINE, ELECTRICITY_UTILITY, PACKING, SCRAP_RECOVERY and an industry BENCHMARK — set company-wide or overridden per machine). **buy-prices** is the other side of the coin: what a supplier charges for the same bottle finished, landed. **breakdown-categories** is the pick-list for why a machine stopped (Machine, PM Short, RM Short, Labour Short). The **make-vs-buy** report puts the two together: for each bottle size over a date range it compares what it actually cost us to blow (preform + electricity + labour + packing − scrap, plus fixed cost spread over volume) against the supplier's landed buy price, and returns a per-bottle delta, a breakeven volume, period savings and a MAKE / BUY / NO_BUY_PRICE verdict. The live data lives in **JIVO_OIL** — 1.24 lakh bottles blown in July 2026 at ₹9.87 lakh net cost, verdict MAKE with ₹40,609 saved on the 50g size.

### Traps

1) THE DATA IS IN JIVO_OIL, NOT MART. Every blowing list returns 200 with [] on JIVO_MART — the module IS enabled there, it simply has no data. JIVO_OIL is the live book (9 runs, 1.24 lakh bottles in July 2026, 2 preform specs, 1 machine, the only buy price, the only breakdown categories). JIVO_BEVERAGES holds a pilot setup (1 machine, 1 preform spec, 2 DRAFT runs with zero production, 2 rate configs). A CLI that defaults to Oil will find data; one that defaults to Mart will look broken.

2) THE FOUR REPORT ENDPOINTS AND /audit/ ARE NOT BROKEN — THEY 400 WITHOUT PARAMS. The company matrix shows 400/400/400 for reports/daily, reports/monthly, reports/make-vs-buy, reports/variances and audit. That is a missing-required-param error, not a dead route. All five returned clean 200s once given their params. The error body names the param verbatim.

3) EVERY BLOWING ERROR USES THE `detail` ENVELOPE. All five 400s came back as {"detail": "..."} — the DRF-detail style. Blowing does not use the {"error": …}, {"code": …, "error": …} or field-level {"whs": [...]} styles seen elsewhere in this API. A blowing command only needs to read `detail`.

4) NO PAGINATION ANYWHERE IN THIS DOMAIN. Nine list endpoints return a bare JSON array; five return a single JSON object. Nothing returns results/count/next/previous. A --page / --page-size flag would be meaningless on all fourteen.

5) `total_cost` IS NOT THE COST OF THE BOTTLES. In the daily and monthly reports, `total_cost` is the blowing *conversion* cost only. Verified arithmetic for JIVO_OIL July 2026: operator 10,000 + labour 15,600 + wastage 1,593.35 + electricity 38,931.30 = 66,124.65 = total_cost — while `net_cost` is ₹9,86,933.14 because it includes the preform (~₹9.21 lakh). Always quote net_cost as the cost of the bottles.

6) `avg_per_bottle_cost` IS NOT net_cost ÷ production. The monthly report for OIL July 2026 reports avg_per_bottle_cost 6.480 while 9,86,933.14 ÷ 1,24,567 = 7.92. It is an unweighted average across runs, so short/aborted runs drag it. If an operator asks "what did a bottle cost us last month", compute net_cost ÷ total_counter_production yourself and say so.

7) MAKE-VS-BUY `totals.make_cost` AND `totals.buy_cost` ARE NOT COMPARABLE WHEN ANY ROW IS NO_BUY_PRICE. Verified on OIL: make_cost 9,86,933 covers both bottle sizes, buy_cost 7,68,519 covers only the 50g size that has a buy price (85,391 × ₹9.00). Printing them side by side would say "buying is ₹2.2 lakh cheaper" when the verdict is MAKE with ₹40,609 of savings. Only `period_savings`, `delta_per_bottle` and `verdict` are apples-to-apples; the two cost columns are not. Flag NO_BUY_PRICE rows loudly.

8) THE VARIANCE REPORT'S BREACHES ARE CURRENTLY A DATA-ENTRY ARTEFACT, NOT A PRODUCTION PROBLEM. `make_cost.std` is read from preform_spec.std_make_cost_per_bottle. At JIVO_OIL that field on spec 8 holds ₹0.5000 — the *blowing-conversion* benchmark — while `make_cost.actual` is the FULL per-bottle cost including the ₹7.90 preform (₹8.52). Result: every completed OIL run reports a ~1600% breach. The 40g spec has std=null so its runs report "no std". Do not let a command headline "6 of 6 runs breach standard" without that caveat.

9) TWO OVERLAPPING RATE MASTERS. /blowing/rate-configs/ is the older dated sheet (rates per day / per bottle, effective_from); /blowing/cost-rates/ is the newer category+basis Cost Master with per-machine overrides. What actually drives a run's Net Cost is the cost-rates vocabulary: run 13 on OIL has rate_config = null yet fully populated cost_lines carrying `category`/`basis` fields that only exist in the cost-rates model (ELECTRICITY_MACHINE PER_UNIT ₹7.0000, LABOUR PER_PERSON_DAY ₹600.0000). Confidence ~85% — the residual is that both masters happen to hold identical numbers at OIL, so a silent fallback to rate-configs cannot be excluded by arithmetic alone. Show both when an operator asks "what rate are we costing at".

10) /blowing/cost-rates/?machine_id=N RETURNS OVERRIDES ONLY. It returned [] for OIL machine 2 — that means "inherits the company-wide rate", not "no rate configured". To show the effective sheet you must fetch scope=global and overlay the machine rows.

11) `run_number` IS NOT UNIQUE. It restarts at 1 each day (OIL has three different runs numbered 1, on 07-31, 08-01 and 08-03). Key on `id`; display "#run_number · date".

12) TWO STATUS FIELDS, DIFFERENT VOCABULARIES. `status` is stored (DRAFT | IN_PROGRESS | COMPLETED); `live_status` is derived (DRAFT | RUNNING | BREAKDOWN | STOPPED | COMPLETED) and is what the operator sees. The app renders IN_PROGRESS as "Stopped". Separately, `warehouse_approval_status` (NOT_REQUESTED | PENDING | APPROVED | PARTIALLY_APPROVED | REJECTED) gates whether production may start at all — a run stuck at NOT_REQUESTED is waiting on the preform request, not on the machine.

13) ALL MONEY AND DECIMALS COME BACK AS STRINGS ("7.8950", "223970.25") in the master and run endpoints, but as JSON NUMBERS in the report endpoints. Cast before arithmetic or comparisons.

14) QUANTITIES ARE PER BOTTLE (pcs), and preform consumption is in GRAMS. total_preform_g 1,200,000 = 1.2 tonnes of preform. `total_units` means electricity units (kWh), not bottles — an easy misread.

15) ids ARE PER-COMPANY. machine id 2 is OIL's Synergy 1/4; machine id 1 is BEVERAGES' Sidel. Never carry an id across a --company switch.

16) /blowing/sap/items/ USES SAP's PascalCase KEYS (ItemCode/ItemName/UomCode) unlike the rest of the domain, is capped at 50 rows, and JIVO_OIL's item master contains a junk row whose three fields are all the  control character. UomCode can be null.

17) NAME COLLISION: /blowing/breakdown-categories/ and /production-execution/breakdown-categories/ are different tables with independent ids. Same for machines. Do not join them.

## Dashboards & reporting

*10 read commands · 1 write endpoints excluded*

This is the factory app's read-only reporting corner — the five "management dashboard" screens the plant and purchase teams open when they want to know what stock is sitting where, how old it is, what has stopped moving, and whether next month's sales plan can actually be built from what's on hand. Everything here is a live read against SAP HANA (or, for the sales plan, a Postgres cache of a HANA stored procedure); nothing here is transactional data entry. Four surfaces: **Stock Benchmark** (`/dashboards/stock/`) compares on-hand against each item's minimum-stock benchmark per warehouse and flags healthy / low / critical, with a point-in-time twin (`/dashboards/stock/as-of/`) that reconstructs any past date from SAP's inventory-movement ledger (OINM). **Inventory** (`/dashboards/inventory-age/report/`) is the ageing and valuation report — every item x warehouse row with days-in-stock, litres and stock value, plus a warehouse rollup. **Non-Moving** (`/non-moving-rm/report/`) is the dead-stock report: items whose last movement is older than N days, with value at risk and a consumption ratio. **Sales Planning vs Requirement** (`/dashboards/sales-planning-requirement/*`) compares the monthly forecast against stock in hand, minimum stock and open POs to produce a net shortage per item — it is a cached snapshot refreshed by a scheduled job, so it also exposes its own refresh status and a self-describing column-mapping "analysis" endpoint. All ten GET endpoints are routed for all three companies; the Sales Plan report is the one that answers 200 but holds no data for JIVO_MART.

### Traps

1) NO ENDPOINT IN THIS GROUP USES DRF PAGINATION, and only three paginate at all. /dashboards/stock/, /dashboards/stock/as-of/ and /dashboards/sales-planning-requirement/report/ use a custom data[]+meta{page,page_size,total_pages,...} envelope (the sales-plan one additionally has has_next/has_previous instead of total_pages-only). The other seven return their FULL result set with no page params — generating --page/--page-size for inventory-age-report or non-moving-report would be meaningless, and inventory-age-report on JIVO_OIL is 2,418 rows / ~820 KB in one response, so the CLI needs a streaming or file-output path rather than a pager. Where paging exists, page_size is capped at 200 in both places (verified: 400 "Ensure this value is less than or equal to 200").

2) A FIFTH ERROR ENVELOPE, not in the four listed in the brief. Every validation failure in this domain is nested DRF: {"detail":"Invalid query parameters.","errors":{"<field>":["This field is required."]}} — confirmed live on /dashboards/stock/as-of/ (as_of_date), /non-moving-rm/report/ (age), /dashboards/stock/{id}/warehouses/ (warehouse) and on out-of-range page_size. Enum failures use the same shape with a different message: {"errors":{"status":["\"bogus\" is not a valid choice."]}} on the sales-plan report, and {"errors":{"status":["Invalid status values: all. Allowed: critical, healthy, low, unset"]}} on the stock dashboard. A handler that only looks at top-level "error"/"detail" will print "Invalid query parameters." and throw away the one thing the operator needs — the field name.

3) THE NON-MOVING REPORT LIES WHEN YOU OMIT item_group. age is the documented required param, but omitting item_group returns an empty report with meta.item_group=0 — it is group-zero, not "all groups". `non-moving-report --age 45` would tell an operator there is no dead stock when JIVO_OIL actually has 293 non-moving packaging items worth ₹58.2 lakh. Make item_group required in the CLI, or default it the way the UI does (the Packaging Material group).

4) item_group IS A NAME IN ONE REPORT AND A CODE IN THE OTHER. /dashboards/inventory-age/report/ and /dashboards/stock/ take the group NAME ('PACKAGING MATERIAL'); /non-moving-rm/report/ takes the numeric CODE (105). Same parameter name, two types, adjacent commands.

5) /non-moving-rm/item-groups/ IS NOT COMPANY-SCOPED AND IS WRONG FOR JIVO_OIL. All three companies return a byte-identical payload (verified by MD5). Its mapping matches Beverages. On Oil it calls code 112 "FA CONSUMABLES" while the report returns 368 rows of "FIXED ASSETS" for that code, and it offers code 110 as "FIXED ASSETS" which yields 0 rows because Oil has no group 110. Resolve group codes from /dashboards/inventory-age/filter-options/ instead — that one IS company-scoped (three genuinely different payloads, verified live).

6) MULTI-VALUE RULES ARE INCONSISTENT BETWEEN THE TWO REPORT FAMILIES. On /dashboards/stock/ and /dashboards/stock/as-of/, warehouse / status / movement_status accept comma-separated lists and they work. On /dashboards/inventory-age/report/, warehouse / sub_group / variety are SINGLE-VALUE: a CSV is treated as one literal string and returns 0 rows, and repeating the param twice silently keeps only the last. Both proven live. A shared "list param" helper in the generated CLI would break inventory-age silently.

7) 'all' IS NOT A STOCK STATUS. The UI's status dropdown contains {value:"all"} but that is a client sentinel — sending status=all gets a 400. Allowed values, per the API's own message: critical, healthy, low, unset. Separately, the most common value in responses, "none" (no benchmark and nothing on hand — 109,010 of JIVO_OIL's 127,065 rows), is not selectable by any filter value, so applying ANY status filter silently drops ~86% of the rows.

8) SELECTING 2+ WAREHOUSES ON THE STOCK DASHBOARD MERGES ROWS. With warehouse=BH-BS,BH-PM the API returns one row per item with warehouse="2 warehouses" and warehouse_count=2, not two rows. The per-warehouse numbers are only recoverable via /dashboards/stock/{item_code}/warehouses/. An operator reading on_hand off a merged row is reading a sum across warehouses.

9) THE AS-OF SNAPSHOT MIXES ERAS. The API states it itself: on-hand and movement age are reconstructed from SAP OINM, but min_stock and item-master fields are CURRENT values. So health_ratio on a past date is a past quantity over today's benchmark. Anyone comparing month-end health ratios over time is comparing against a moving baseline.

10) AGE FILTERS DISAGREE ON INCLUSIVITY. /non-moving-rm/report/?age=45 is STRICT (lowest days_since_last_movement returned was 46); /dashboards/inventory-age/report/?min_age=90 is INCLUSIVE (lowest days_age was exactly 90). Verified both.

11) SALES-PLAN DATA IS SNAPSHOTTED AND CAN BE MONTHS STALE, AND MART HAS NONE. The report reads a Postgres cache, not SAP live. Beverages' cache was last loaded 2026-06-04 against "PLANNING OF MAY MONTH" — two months old today. Mart answers 200 with an empty report and null refresh status because it is not in supported_companies. Any command that prints these numbers should print refresh.last_success alongside them, and should distinguish "not run for this company" from "no shortages". There is also no forecast_id filter — I passed one and it was ignored; only the latest forecast exists, because the loader replaces all rows for the company.

12) 502/503 MEANS SAP IS DOWN, NOT THAT THERE IS NO DATA. The stock, inventory-age, non-moving and sales-plan screens all special-case exactly 502 and 503 to show an "SAP unavailable" banner with a retry. A CLI that reports those as an empty result set will have operators concluding the warehouse is empty during a HANA outage.

### Confidence & open questions

HIGH / live-verified today (2026-08-03): all ten GET paths exist and return 200; every required param and its exact 400 body; page_size cap of 200 on both paginating endpoints; the stock status enum (quoted from the API's own error); the sales-plan status enum and its 400; that /non-moving-rm/report/ returns nothing without item_group; that its age filter is strict while inventory-age's min_age is inclusive; that inventory-age accepts warehouse/sub_group/variety server-side but only single-valued and last-wins; that /dashboards/stock/ accepts CSV for warehouse/status/movement_status and merges rows across 2+ warehouses; that /non-moving-rm/item-groups/ is byte-identical across the three companies and mis-maps codes for JIVO_OIL (proven by 112→FIXED ASSETS/368 rows and 110→0 rows); that the sales-plan status endpoint is inert across repeat calls; and that /dashboards/stock/{item_code}/warehouses/ works on JIVO_OIL and JIVO_MART.

MEDIUM / inferred, say so if it matters: (a) /dashboards/stock/{item_code}/warehouses/ on JIVO_BEVERAGES — not called, inferred from identical routing and its 200 siblings there; (b) movement_status on the as-of path — the client sends it through the shared builder and the two paths share a serializer, but I only proved status/sort_by/sort_dir/warehouse there; (c) the exact allowed set for movement_status (recent|slow) comes from the UI options and from every response I saw, not from an API error listing them — I deliberately did not probe an invalid value to make it enumerate, per the no-guessing rule.

WHAT I DID NOT DETERMINE: whether the stock dashboard's `search` is case-sensitive server-side (the client always upper-cases, so I only ever sent upper-case); the upper bound on as_of_date (how far back OINM reconstruction stays correct); and whether inventory-age's item_group would also accept a numeric code (I only sent names, which the UI sends).

SIDE-EFFECT RISK: I judge all ten read endpoints "none", not merely unproven. None of them takes a lookup key and returns a single id/created_at/updated_at object — the two that take a key (stock item-warehouses, and the group/date filters) return lists, and the two that return id-bearing objects (sales-plan status and the report's embedded refresh block) accept no key at all and were shown stable across repeat calls. Nothing in this group resembles the /marketplace/settings/ get_or_create pattern. The one mutating path, .../refresh/, is POST-only and excluded outright.

## Dispatch, dispatch plans & docking

*17 read commands · 14 write endpoints excluded*

The dispatch domain follows a SAP sales invoice from the moment it becomes a "dispatch bill" to the moment the truck clears the gate and the transporter gets paid. /dispatch-plans/ is the planning half: it lists SAP invoices in a date window with the factory's own planning overlay on top (vehicle, transporter, driver, bilty/LR, freight, planned dispatch date), plus a live vehicle board (the "pipeline", 10 stages from Booked -> Empty Vehicle In -> Ready to Dock -> Docked -> Photo Attached -> Ready for Gatepass -> Gatepass Printed -> Print Committed -> Dispatched / Rejected) and a fulfilment dashboard comparing what was billed against what actually left. /dispatch/ is the money half: "bilty GRPO" turns a transporter's bilty into a service GRPO posted to SAP (freight booked as a purchased service), and the resulting "open bilties" are later rolled up into one transporter A/P invoice. /docking-admin/ is the exception queue at the dock: when the barcode scan count does not match the invoice, the docking operator files a partial-scan request ("515 of 521 scanned, 6 box short") or a scan-skip request ("118 box old barcode"), and a supervisor (Bhupinder Singh / Amit Pal Singh in the live data) approves or rejects it with a note. Everything readable here is a queue or a board that a dispatch supervisor watches through the day, so the numbers move minute by minute. All 17 GET endpoints are routed for all three companies; the actual write actions (booking a plan, posting a GRPO, posting an A/P invoice, approving a scan exception) all live on POST/PATCH paths and are excluded.

### Traps

1) CROSS-COMPANY DASHBOARDS — the single biggest trap. /dispatch-plans/dashboard/summary/ and /dispatch-plans/dashboard/bills/ IGNORE the Company-Code header and always aggregate JIVO_OIL + JIVO_MART + JIVO_BEVERAGES. Proven live: identical count (80) and identical results[0] under both a JIVO_OIL and a JIVO_BEVERAGES header, the summary's own filters.company_codes lists all three with company_count 3, and a row fetched under JIVO_OIL carried gatepass_no "DCK/JIVO_BEVERAGES/2026-27/000511". There is no param to scope them. Any command built on these two MUST print "all three companies" next to the number, or Accounts will read a group figure as their own company's. Every other endpoint in this domain IS company-scoped.

2) /dispatch/bilty-grpo/pending/ SILENTLY DEFAULTS TO THE CURRENT MONTH. Reproduced three times on JIVO_OIL: no params -> count 12, byte-for-byte the same as year=2026&month=8; year=2026&month=7 -> count 157. A naive "show me pending bilty GRPOs" command reports 12 when the real backlog is an order of magnitude larger. Worse, the month filter is not a filter on dispatch_date — the month=8 result contained rows dated 2026-06-18 and 2026-07-14 — so I could not determine which date column it keys off. Always pass year+month explicitly and never present the unfiltered count as "all pending". (History does NOT behave this way: a bare call returned all 35 rows across months.)

3) `limit` ON /dispatch-plans/bills/ CORRUPTS THE TOTALS. It is a hard row cap, not a page, and meta is recomputed on the capped set — verified live: meta.total_bills was 4 unlimited and 1 with limit=1. Never sample with limit and then quote meta. There is no offset/page on this endpoint at all; it returns the whole window.

4) THE UI DEFAULT AND THE SERVER DEFAULT DISAGREE on Jivo Mart transfers. The Dispatch Plans screen ticks exclude_jivo_mart_transfer ON; the API defaults it OFF. Verified live: 4 bills without the flag, 1 with it — three of the four were Oil->Jivo Mart intercompany stock transfers. A CLI that mirrors the API will show a bigger number than the screen the operator is used to.

5) by_dispatch_date=true SILENTLY CHANGES WHAT date_from/date_to MEAN — from the SAP invoice date to the planned dispatch date. Verified live: the same window returned 4 rows normally and 26 rows with the flag, including bills invoiced in July.

6) all_companies is spelled differently per endpoint family: it is "1" on /dispatch-plans/bills/ and /dispatch-plans/pipeline/ (verified live: pipeline total 26 -> 90), and it does not exist on the two dashboard endpoints (which are already cross-company). company_code is only populated on bill rows when all_companies is set; it is null otherwise.

7) FIVE DIFFERENT RESPONSE ENVELOPES INSIDE ONE DOMAIN — do not generate one pagination flag for the group. /dispatch-plans/bills/ = {data, meta}; /dispatch-plans/dashboard/bills/ = {count, limit, offset, status_counts, results} (offset pagination); /dispatch/bilty-grpo/pending|history/ = {results, count, page, page_size, total_pages, next, previous} where next/previous are PAGE NUMBERS (2) not URLs; /dispatch-plans/pipeline/ = {columns, cards, meta}; and /dispatch/open-bilties/, both /docking-admin/ lists and /dispatch/transporter-invoices/history/ are BARE ARRAYS with no envelope at all. page_size on the DRF ones is capped at 100 (I asked for 200 and got 100).

8) "ALL" IS NEVER A VALUE — it is the absence of the param. This applies to booking_status on /dispatch-plans/bills/, status on /dispatch-plans/dashboard/bills/, and status on both /docking-admin/ lists. Sending status=ALL or booking_status=all is not something the app ever does and I did not test it (that would be inventing a value against a live API).

9) TWO PATHS NAMED "preview", ONE READ AND ONE WRITE. GET /dispatch/bilty-grpo/preview/{dispatch_plan_id}/ is the safe read. POST /dispatch/transporter-invoices/preview/ is a write-verb path that returns 405 to GET. Do not let a name-based generator conflate them.

10) THE ID NAMESPACES ARE EASY TO CROSS. /dispatch/bilty-grpo/preview/{id}/ takes a dispatch_plan_id; /dispatch/bilty-grpo/{id}/ takes a service-GRPO posting id; /dispatch-plans/bills/{id}/plan/ takes a SAP invoice doc_entry; /docking-admin/*/by-sales-dispatch/{id}/ takes a sales_dispatch id. Four different keys, all bare integers, all in adjacent commands.

11) LEGACY ALIASES ARE STILL LIVE — /grpo/service/pending/, /grpo/service/history/ and /grpo/service/preview/{id}/ return payloads identical to their /dispatch/bilty-grpo/* twins (verified live: same 12-row payload, same count 35, same preview object). The current spec.yaml ships the /grpo/service/preview/ form. Pick one family or the CLI will carry duplicate commands for the same data.

12) ERROR ENVELOPE — this whole domain uses the DRF `{"detail": ...}` style, in two flavours: `{"detail":"Method \"GET\" not allowed."}` for the write-only paths and `{"detail":"Invalid query parameters.","errors":{"date_from":["This field is required."]}}` for the missing-param case on /dispatch-plans/bills/. The nested `errors` map is where the required param names are, and it is what a good CLI error message should surface. None of the other three envelope styles in this API appear here.

13) THE DATA MOVES WHILE YOU LOOK AT IT. Within five minutes of live probing, /dispatch-plans/dashboard/bills/ status_counts went from BOOKED 22 / DISPATCHED 39 to BOOKED 18 / DISPATCHED 43 as four trucks left. The pipeline UI polls every 30s. Any report from this domain needs a timestamp; the summary endpoint helpfully returns filters.from/to and the bills endpoint returns meta.fetched_at.

14) Empty is not broken. JIVO_MART has zero bilty-GRPO history and zero open bilties; JIVO_BEVERAGES has zero partial-scan requests; /dispatch/transporter-invoices/history/ is empty in all three. These are true empties on a live 200, and the CLI should say so rather than implying a fault.

## GRPO — goods receipt against PO

*14 read commands · 7 write endpoints excluded*

GRPO = "Goods Receipt PO" — the step where material that has physically arrived at a JIVO plant gets booked into SAP as a purchase receipt. It has two completely separate halves that share the /grpo/ prefix. (1) MATERIAL GRPO: a truck arrives, security books a gate entry, stores raises an arrival slip, QC inspects and accepts/rejects quantities, and only then does a GRPO operator push the accepted quantity into SAP against the purchase order. /grpo/all-entries/ is the live board of every raw-material gate entry with a phase of GATE (still at the gate), QC (with the lab), or DONE; /grpo/pending/ is the shorter list of entries that have cleared QC and are waiting to be posted; /grpo/history/ is the log of every posting attempt with its SAP document number or its SAP error. (2) SERVICE GRPO: the freight side — after a dispatch vehicle has gone out, the transporter's bilty (consignment note) is booked as a service purchase receipt against the transporter's vendor account, so the freight cost lands in SAP. /grpo/service/pending/ lists dispatched plans whose freight has not been booked, /grpo/service/history/ the freight postings. Attachments (supplier invoice / bilty PDFs) are pushed to SAP alongside the document. Everything here is a staging-and-audit layer in front of SAP — the factory app records the attempt, SAP holds the truth. Right now the material half is broken: on JIVO_OIL the last successful post to SAP was 2026-07-15 and every attempt since (latest 2026-07-28) failed on the SAP attachment uploader.

### Traps

1) /grpo/draft/ HTTP 500 — VERDICT: a REAL route with a REAL server bug, and it must NOT be published. Evidence: OPTIONS /grpo/draft/ returns 200 with `Allow: GET, POST, PATCH, DELETE, HEAD, OPTIONS` and the view's own docstring, which documents GET only on `/grpo/draft/<id>/`. One APIView class is mounted at both /grpo/draft/ and /grpo/draft/<id>/; on the collection mount there is no posting_id kwarg, so get() raises and Django serves its bare HTML 500 page. Identical 500 on all three companies. There is NO "list all drafts" capability anywhere in this API — do not synthesise one.

2) The current shipped spec.yaml has two DEAD paths in this group. /grpo/history/{posting_id}/ and /grpo/service/history/{posting_id}/ both return 404 (verified with real ids 507 and 220). The real routes are /grpo/{posting_id}/ and /grpo/service/{posting_id}/. Any CLI built from the existing spec has two broken commands today.

3) FIVE error styles, not four. On top of the four JSON envelopes, this group emits raw Django HTML for router-level 404s and for the 500 — /grpo/history/507/ returned `<!doctype html><title>Not Found</title>`, /grpo/draft/ returned `<title>Server Error (500)</title>`. A CLI that json-decodes every error body will crash on both. DRF's own 404s ARE JSON ({"detail":"No RawMaterialInspection matches the given query."}) — so the same command can get either style depending on whether the URL or the object is missing.

4) /grpo/service/pending/ SILENTLY DEFAULTS TO THE CURRENT MONTH; nothing else in this group does. JIVO_OIL on 2026-08-03: no params = 12 rows, year=2026&month=7 = 157. The server docstring admits it. Every other list (history, pending, all-entries, service/history) returns all-time when year/month are omitted. A naive "how much freight is pending?" command would under-report by 13x.

5) page_size is hard-capped at 100. Asking 500 returns page_size 100. next/previous in the DRF envelope are PAGE NUMBERS (integers) or null — NOT URLs — so a generic "follow next link" pager will break.

6) Three different id spaces, all called "id" somewhere: posting_id (history row id → /grpo/{id}/, /grpo/{id}/attachments/, /grpo/draft/{id}/), vehicle_entry_id (→ /grpo/preview/{id}/, and the ?vehicle_entry_id= filter), arrival_slip_id (→ /grpo/inspection-report/{id}/), dispatch_plan_id (→ /grpo/service/preview/{id}/ and the ?dispatch_plan_id= filter), service posting_id (→ /grpo/service/{id}/). Crossing them yields a 404 or, worse, a plausible wrong record. Never enumerate any of them — always read the id out of the list endpoint first.

7) /grpo/history/ is an ATTEMPT log, not a posted-documents list. It contains DRAFT and FAILED rows with sap_doc_num=null. And summary.failed_count ≠ COUNT(history?status=FAILED): OIL shows 14 vs 19, the gap being exactly the 5 rows with is_superseded=true (retried attempts). Whichever the CLI reports, it must say which definition it used.

8) Shape traps: /grpo/preview/{id}/ and /grpo/{id}/attachments/ return BARE ARRAYS, not objects — unusual for detail-shaped endpoints and enough to break a generated dict-assuming formatter. /grpo/service/options/ is a 116-168 KB object of nine master-data arrays and should never be dumped whole.

9) Alias duplication: /grpo/service/history/, /grpo/service/preview/{id}/, /grpo/service/pending/ (and options) are byte-identical twins of /dispatch/bilty-grpo/history/, /preview/{id}/, /pending/, /options/. Verified identical for history. The shipped React app calls the /dispatch/bilty-grpo/* side even though its own ENDPOINTS constant declares GRPO.SERVICE_*. If the dispatch domain also publishes them, the CLI will ship the same data twice under two names.

10) Company reality, not permissions: all 20 GRPO routes are routed for all three companies (no 403 anywhere in this group — the marketplace module gating does not touch GRPO). But MART has NO material GRPO data at all (pending 0, history 0, summary all zeros, 5 gate entries stuck at QC) while having a busy freight side (service-pending 101 for July). Report "MART books no material GRPOs", never "no permission" and never "no data available".

11) THE MATERIAL GRPO → SAP FEED IS CURRENTLY BROKEN, and any command that reports pending counts should say so. JIVO_OIL: last successful post 2026-07-15 (entry GE-2026-1362, SAP 2026076623); latest attempt 2026-07-28, all failed; error_message values are 'Unable to connect to SAP file uploader', 'SAP file uploader authentication failed', 'SAP attachment metadata registration failed after uploader success' and raw SAP errors -1116 / -5002. 327 entries sit pending on OIL, 39 on BEVERAGES. This matches the 2026-07-30 note that the factory GRPO feeder had been dead ~15 days — it is now ~19 days and nobody has retried since 28 July.

12) Quantities in this group are raw SAP UoM and MIX units across items in one payload (MTS for oil, PCS for cartons). qc_accepted_qty in /grpo/summary/ is a straight sum across both — it is not a tonnage and must not be presented as one.

## Gate core

*53 read commands · 35 write endpoints excluded*

gate-core is the shared gate engine underneath every category-specific gate app (raw-material, daily-needs, maintenance, construction, fixed-asset gatein). Its central object is an **arrival** — one physical truck at the plate, from gate-in to gate-out — and everything else hangs off it. A truck arrives (arrival), gets a gate-in entry per company it is loading for (empty-vehicle-in), is docked and loaded against SAP invoices/stock-transfers (sales-dispatch, called "Sales Dispatch Out" / "docking" in the UI), gets a gatepass printed and committed, is marked dispatched, and then is followed on the road (dispatch-tracking). The same engine also handles the other outbound flows the gate sees: BST (branch stock transfer) out, job-work material out-and-back, rejected-QC material leaving, and empty vehicles leaving. Two SAP lookup families sit here so the gate clerk can attach the right SAP document without leaving the screen: stock-transfer lookup for BST-out and GRPO/production-order lookup for job-work. The pipeline the whole app is built around is a fixed ladder — BOOKED → EMPTY_IN → READY_TO_DOCK → DOCKED → PHOTO_ATTACHED → READY_FOR_GATEPASS → GATEPASS_PRINTED → PRINT_COMMITTED → DISPATCHED, with REJECTED as the off-ramp. Crucially, an arrival is a *truck*, not a company: a single arrival routinely carries bills for Oil, Mart and Beverages at once, which is why the arrival-level endpoints return identical data regardless of the Company-Code header while the company-level ones do not.

### Traps

1) DUAL-USE PATHS — 12 of the readable gate-core paths also accept a write verb on the SAME url, so an is_mutation flag would have been false for all of them: /gate-core/arrivals/ (GET+POST), /gate-core/bst-outs/ (GET+POST), /gate-core/bst-outs/{id}/ (GET+PUT), /gate-core/empty-vehicle-ins/ (GET+POST), /gate-core/empty-vehicle-ins/{id}/ (GET+PATCH), /gate-core/empty-vehicle-outs/ (GET+POST), /gate-core/job-work/ (GET+POST), /gate-core/job-work/{id}/ (GET+PUT), /gate-core/rejected-qc-returns/ (GET+POST), /gate-core/sales-dispatch/ (GET+POST), /gate-core/sales-dispatch/{id}/ (GET+PATCH), /gate-core/sales-dispatch/lock/ (GET+PATCH), /gate-core/sales-dispatch/{id}/attachments/ (GET+POST), /gate-core/sales-dispatch/{id}/box-scans/ (GET+POST), /gate-core/dispatch-tracking/{id}/updates/ (GET+POST), /gate-core/gate-attachments/{id}/ (GET+POST). Every one is published GET-only and the write verbs are deliberately dropped.

2) THE ONE SIDE-EFFECT SUSPECT — /gate-core/sales-dispatch/lock/ must NOT become a command. Three per-company singleton rows with three different created_at values and changed_by null on all three is the fingerprint of a get_or_create firing on read. See its endpoint notes. Every other gate-core GET I checked either returns a list or returns a computed object with no id/created_at (/arrivals/expected/, /gatepass/readiness/, /barcode-scans/), so lock is the only one.

3) /gate-core/job-works/ IS A PHANTOM — 404, verified live. The harvest emitted it because the ENDPOINTS constant NAME is `JOB_WORKS` while its VALUE is `/gate-core/job-work/` (singular). Publishing it would ship a permanently broken command. The real list is /gate-core/job-work/.

4) PAGINATION IS NOT UNIFORM — THREE different behaviours in one domain group. (a) /gate-core/dispatch-tracking/ always returns an envelope {results, count, page, page_size, total_pages, next, previous} where next/previous are BOOLEANS, not URLs — a client that follows next as a link will break. (b) /gate-core/sales-dispatch/ is HYBRID: no page param → bare unpaginated array; with page → envelope {count, num_pages, page, page_size, results} — note num_pages, NOT total_pages, and no next/previous at all. (c) Every other gate-core list is a bare array and SILENTLY IGNORES page/page_size — verified on arrivals, empty-vehicle-ins and sales-dispatch/documents, all of which returned their full unpaginated set when sent ?page=1&page_size=2. A blanket --page/--page-size flag would lie on most of this group.

5) SILENT TRUNCATION, three different caps, none of them announced in the payload. /gate-core/arrivals/ returns only the newest 200 arrivals (ids 540-739, 12 days of history) — and it IGNORES from_date/to_date entirely: a July window returned the identical last-200 rows. There is no way to reach older arrivals from this endpoint at all; use /gate-core/sales-dispatch/ or /gate-core/dispatch-tracking/ for history. /gate-core/sales-dispatch/documents/ caps at 100 rows PER document_type (200 total) after filtering — a June-only window came back as 100 invoices all dated 2026-06-30, so wide windows silently drop rows; if a type comes back with exactly 100 rows, the answer is incomplete. The three SAP lookups (bst-outs/sap-transfers, job-work/sap-grpos, job-work/sap-production-orders) return 50 rows and are meant to be driven by ?search=, which is verified working on all three.

6) COMPANY SCOPING IS SPLIT DOWN THE MIDDLE, and getting it wrong silently halves an answer. TRUCK-LEVEL endpoints ignore the Company-Code header and return the same data everywhere: /gate-core/arrivals/, /gate-core/dispatch-tracking/, /gate-core/inside-dispatch-vehicles/, /gate-core/unit-choices/, /gate-core/empty-vehicle-ins/reasons/ (all confirmed by byte-identical payloads across the three headers). COMPANY-LEVEL endpoints do scope: sales-dispatch (MART 142 / OIL 210 / BEV 514), empty-vehicle-ins (143/211/537), empty-vehicle-outs (5/55/50), eligible-entries (150/943/1047). For those, ?all_companies=1 lifts the scope — verified live: a MART-headed 3-day sales-dispatch query went from 7 rows to 30 across all three companies. Because one truck routinely carries Oil, Mart and Beverages bills at once, any "what was on that truck" question needs all_companies=1 or it will be wrong.

7) SIZE HAZARDS that will hang a terminal. /gate-core/sales-dispatch/reports/ returned 18.8 MB (OIL) and 27.8 MB (MART) unfiltered, and STILL 9.6 MB for a three-day window covering six dispatches, because every row embeds its full box_scans[] array. The useful part is the 194-byte `counts` object. /gate-core/sales-dispatch/{id}/ and /by-vehicle-entry/{id}/ are 664 KB for a SINGLE record. /gate-core/sales-dispatch/{id}/box-scans/ was 678 KB / 1067 rows for one dispatch. None of these should be dumped raw by the CLI or handed to an MCP tool unfiltered.

8) THE STATUS LADDER IS THE DOMAIN LANGUAGE — hard-coding a different vocabulary will confuse operators. The pipeline is BOOKED → EMPTY_IN → READY_TO_DOCK → DOCKED → PHOTO_ATTACHED → READY_FOR_GATEPASS → GATEPASS_PRINTED → PRINT_COMMITTED → DISPATCHED, with REJECTED off to the side, and the bundle ships plain-English glosses for each ("pending at gate", "docked at dock", "pending at sales dispatch out", "dispatched at sales dispatch out"). Arrival status is a different, shorter enum — INSIDE / LOADING / DEPARTED. dispatch-tracking uses a third one — DISPATCHED, IN_TRANSIT, REACHED_DESTINATION, UNLOADING, DELIVERED, PARTIALLY_DELIVERED, RETURNED, DELAYED, CLOSED. Three enums, three fields called "status".

9) JOB-WORK'S DISPLAYED STATUS IS COMPUTED, NOT STORED. The UI shows CANCELLED if status==CANCELLED; else PENDING if there is no production order; else COMPLETED if status==COMPLETED; else IN_PROGRESS. Printing the raw `status` field will disagree with what the operator sees on screen.

10) pending-bookings ids ARE NOT INTEGERS — a row's id is a string like "booking:1919,1921,1920,1922" because one pending booking groups several dispatch plans onto one truck. Typing it as int, or passing it to sales-dispatch-detail, will fail.

11) SIX ENDPOINTS RETURN 200 WITH AN EMPTY ARRAY IN ALL THREE COMPANIES and that is the correct business answer, not a fault: bst-ins, bst-ins/eligible-outs, bst-outs, bst-returns, bst-returns/eligible-outs, rejected-qc-returns. The BST family under gate-core is legacy — the real BST workload moved to /warehouse/bst/ — while rejected-QC returns genuinely had no activity. A CLI that reports "no data / possible error" here will send operators chasing a non-problem.

12) /gate-core/arrivals/expected/ is the only gate-core endpoint that 400s without a param: {"detail":"vehicle_id is required."} — note the `detail` envelope. Gate-core uses TWO of the four error styles in this API: `detail` (DRF-shaped, on arrivals/expected and on all the 405s) and, per the wider survey, `error` on some others. A gate-core command must read `detail` first and fall back to `error`.

13) SEARCH SEMANTICS DIFFER. ?search= on sales-dispatch matches entry_no / sap_doc_num / customer / vehicle / driver / transporter / gatepass_no / item_summary; on documents it matches doc_num; on the SAP lookups it matches the document number. All verified live. dispatch-tracking's own UI describes its search as "vehicle, arrival, bill, customer, company, status".

## Gate-in by material category

*9 read commands · 14 write endpoints excluded*

These five prefixes are the "what came in the gate" flows, split by what kind of material arrived: raw material / packing material against a purchase order, daily-needs (canteen food and consumables), maintenance (spare parts and tools), construction (civil and building work), and fixed assets (capital equipment). They all hang off the same object: a gate entry IS a vehicle entry — one row per truck at the gate — and `entry_type` on that vehicle entry (RAW_MATERIAL, DAILY_NEED, MAINTENANCE, CONSTRUCTION, FIXED_ASSET, plus JOB_WORK and SALES_DISPATCH elsewhere) decides which of these five modules holds the material detail. Each module exposes the same three-part shape: a small master list (categories / types) the gate clerk picks from, one detail record keyed by the gate-entry id, and a "complete" action that closes the entry. Only the master list and the detail read are GETs; complete/update/delete are writes and are excluded here. Raw material is the odd one out — instead of a single free-text detail it holds PO receipts (which SAP PO, which line, ordered vs received vs short qty), and it runs a 13-state QC pipeline, whereas the other four only ever sit in DRAFT / IN_PROGRESS / COMPLETED. In practice this whole family is a JIVO_OIL story: Oil holds 26 construction, 7 fixed-asset, 161 daily-need, 32 maintenance and 574 raw-material entries; Beverages has a handful; Mart has 5 raw-material entries and literally zero of the other four. There is no list endpoint inside these five prefixes at all — to find a gate entry you must first list vehicle entries by entry_type in the vehicle-management domain, then read the detail here.

### Traps

1) THE {id} IS THE VEHICLE-ENTRY ID, NOT THE DETAIL ID. Every per-entry path in this family is keyed by the gate/vehicle entry id, while the object it returns carries its own unrelated `id` (gate entry 366 returns construction detail id 26; gate entry 2500 returns fixed-asset detail id 7). Feeding the returned id back in will 404. Name the CLI arg `entry_id`, never `id`.

2) THERE IS NO LIST ENDPOINT ANYWHERE IN THESE FIVE PREFIXES. An operator cannot discover gate entries from this domain at all. The only way in is the vehicle-management list: GET /vehicle-management/vehicle-entries/?entry_type=<TYPE>&from_date=YYYY-MM-DD&to_date=YYYY-MM-DD. `from_date` is REQUIRED there (400 {"detail":"from_date query parameter is required"} without it). entry_type enum, verbatim from chunks/vehicle.constants-UuOHDykf.js: RAW_MATERIAL, CONSTRUCTION, FIXED_ASSET, DAILY_NEED, MAINTENANCE, JOB_WORK, SALES_DISPATCH. Note DAILY_NEED is singular even though the URL prefix is `daily-needs-gatein` and the sub-path is `daily-need`.

3) THE CLI'S DEFAULT COMPANY IS WRONG FOR THIS DOMAIN. spec.yaml pins Company-Code: JIVO_MART by default. Mart holds ZERO construction, fixed-asset, daily-need and maintenance gate entries (live-counted 2025-01-01..2026-08-03) and only 5 raw-material entries. Every per-entry command run at the default will look broken. Live counts: CONSTRUCTION Oil 26 / Mart 0 / Bev 0; FIXED_ASSET 7 / 0 / 1; DAILY_NEED 161 / 0 / 3; MAINTENANCE 32 / 0 / 1; RAW_MATERIAL 574 / 5 / 73. Default this group to JIVO_OIL, or print "0 gate entries of this type in <company>" rather than an empty array.

4) THE MASTER LISTS ARE NOT COMPANY-SCOPED. The four categories/types endpoints return byte-identical payloads with identical ids in all three companies. `--company` changes nothing on them. (Verified identical; that they are one shared table is inferred.)

5) TRAILING SLASH ON THE PO-RECEIPTS READ. `/raw-material-gatein/gate-entries/{id}/po-receipts/view` (the form written in the app's own ENDPOINTS constant) returns HTTP 301 with no body to a non-redirect-following client. Use `/po-receipts/view/`. Both spellings are in HARVEST.json as separate rows — they are one endpoint.

6) FOUR PATHS THAT LOOK READABLE ARE WRITE-ONLY, AND ONE OF THEM IS A DELETE. `/raw-material-gatein/gate-entries/{id}/` is DELETE-only — a naive generator will read that as "get gate entry by id" and publish a destructive command. Live-verified GET -> 405 {"detail":"Method \"GET\" not allowed."}. Same for all four `/complete/` paths, all three `/update/` paths, `/maintenance/receive-spare/`, `/po-receipts/`, `/po-receipts/{id}/` and `/po-receipts/{id}/replace/`.

7) DUAL-USE URLS: four of the nine published GETs share their exact URL with a POST that creates the detail record (`/{id}/construction/`, `/{id}/fixed-asset/`, `/{id}/maintenance/`, `/{id}/daily-need/`). Filtering on an "is_mutation"/"write_only" flag would not catch this — HARVEST.json has is_mutation:false and write_only:false on all four. Filter on the methods array and emit GET only.

8) TWO DIFFERENT STATUS VOCABULARIES. Raw material runs a 13-state QC pipeline (DRAFT, SECURITY_CHECK_DONE, ARRIVAL_SLIP_SUBMITTED, ARRIVAL_SLIP_REJECTED, IN_PROGRESS, QC_PENDING, QC_IN_REVIEW, QC_AWAITING_QAM, QC_REJECTED, QC_HOLD, QC_COMPLETED, COMPLETED, CANCELLED). The other four only ever use DRAFT / IN_PROGRESS / COMPLETED (chunks/SharedDashboard-BmuErtun.js). Any shared "status" help text or filter enum must not offer QC states for construction/fixed-asset/daily-need/maintenance.

9) A DETAIL 404 IS NORMAL, NOT AN ERROR. Gate entries are created in step 1 and the material detail is filled in at step 2/3, so a DRAFT (and sometimes IN_PROGRESS) entry legitimately has no detail row and returns 404 "<X> entry does not exist". The CLI should say "no <category> detail recorded yet on entry N", not "not found".

10) ONLY ONE ERROR ENVELOPE IS IN PLAY HERE. Every error this domain emitted live used DRF's {"detail": "..."} — 404 "Construction entry does not exist" / "No VehicleEntry matches the given query.", 405 "Method \"GET\" not allowed." None of the other three envelope styles ({"error":...}, {"code":...,"error":...}, field-level {"whs":[...]}) appeared on any of these nine paths. Still handle all four generically, but the domain-specific message extraction is `detail`.

11) SHAPE IS NOT UNIFORM ACROSS THE FAMILY. fixed-asset and daily-need return items[] arrays; construction and maintenance are single-line objects. Maintenance's master uses `type_name` while the other three use `category_name`. Daily-need's master returns only {id, category_name} with no description/is_active. Quantities come back as decimal STRINGS ("4.00") on the four detail endpoints but as JSON FLOATS (15000.0) inside po-receipts items. Do not generate one shared model.

12) COMPANY SCOPING IS ENFORCED ON THE ID LOOKUP, not just on the list. An Oil entry id read under Company-Code: JIVO_MART returns 404 "No VehicleEntry matches the given query." — no cross-company data leak (verified on entry 366 against both Mart and Beverages).

13) CROSS-DOMAIN COMPANIONS (belong to the gate-core group, not published here, but an operator will want them): /gate-core/construction-gate-entry/{id}/, /gate-core/daily-need-gate-entry/{id}/, /gate-core/maintenance-gate-entry/{id}/ and /gate-core/raw-material-gate-entry/{id}/ each return the WHOLE entry (gate_entry + vehicle + driver + security_check + <category>_details) in one call — verified 200 on construction/366. There is deliberately NO fixed-asset equivalent; that gap is real, not a harvest miss.

14) BUSINESS ENUMS worth surfacing in help text: construction security_approval = APPROVED | PENDING | REJECTED; maintenance urgency_level = NORMAL | HIGH | CRITICAL. Both read out of the UI form selects, not guessed. Do NOT send any value not on these lists to the live API.

15) Construction has only two active categories, one of them "Others", so category filtering is close to meaningless — point operators at material_description / project_name instead.

## Labour count & labour gate

*5 read commands · 14 write endpoints excluded*

This domain covers how JIVO's factory counts contract ("casual") labour on and off the site each day. Two separate Django apps live here and they solve the same problem twice. `labour_gate` (paths under /labour-gate/) is the gate's own tally: the security desk records how many labourers each contractor brought in for a work date and shift, then marks batches out as they leave; every edit is audited. `labour_count` (paths under /labour-count/) is the department-driven version: a department fills a headcount sheet per contractor, submits it to the gate (or it auto-submits at the shift lock time — 18:30 IST for DAY, 06:30 IST next day for NIGHT), and the gate then marks out against that sheet and finalizes it, producing a variance. In live data only the gate flow is actually used: 324 gate entries with daily activity through 2026-08-03, versus 4 labour-count sheets in total across all three companies, the last VERIFIED one dating from 2026-06-25. Note also that /labour-gate/ rows come in two kinds — a row with department = null is the real gate-in headcount for a contractor, and a row with a department set is an informational split of that same headcount across departments, entered on the "Labour" screen. These labour counts are anonymous head tallies against a contractor; they are NOT the named-individual labourer roster at /person-gatein/labours/ (a different agent's domain) and there is no link between the two.

### Traps

1. TWO PARALLEL SYSTEMS, ONE OF THEM DORMANT. `labour_gate` and `labour_count` both count the same thing and do not reconcile with each other. Live counts as of 2026-08-03: labour_gate has ~324 entries with activity every working day through today; labour_count has 4 sheets in existence across ALL THREE companies (OIL 3, BEV 1, MART 0), the newest an empty draft created 2026-08-01 and the only ever VERIFIED one dated 2026-06-25. If an operator asks "how much labour was on site", the answer comes from /labour-gate/, not from labour-count sheets. A command that answers headcount from labour-count would report near-zero and be wrong.

2. /labour-gate/ MIXES TWO ROW KINDS AND SUMMING IT NAIVELY DOUBLE-COUNTS. department == null is the gate-in tally (the real headcount); department != null is an informational allocation of that same headcount across departments, typed on the "Labour" screen. Verified JIVO_OIL 2026-08-03: 3 null-department rows totalling 48 in, plus 3 department rows totalling 9 — the 9 is a subset of the 48, not extra people. Correct totals: labour in = sum(count_in) where department is null and not is_deleted; labour out = sum(total_out) over the same rows; still inside = in − out.

3. SOFT DELETES ARE RETURNED IN THE LIST. Rows carry is_deleted / deleted_by_name / deleted_at / can_restore and stay in the payload. Verified JIVO_OIL 2026-07-28: 22 rows including one deleted. Always filter is_deleted == false.

4. SHIFT IS NOT A SERVER FILTER ON /labour-gate/. The day list returns DAY and NIGHT together; passing shift= is silently ignored (verified: ?date=2026-08-03&shift=NIGHT returned the same 6 DAY rows as without it). Filter on the row's `shift` field. On /labour-count/ endpoints shift IS a real server-side filter/requirement.

5. REQUIRED PARAMS ARE ENFORCED AND THE ERROR STYLE IS UNIFORM. /labour-gate/ without date → 400 {"detail":"A valid ?date=YYYY-MM-DD is required."}. /labour-count/gate/board/ without both work_date and shift → 400 {"detail":"work_date and a valid shift are required."} (work_date alone is still 400). Every error in this domain — including 404s — uses the {"detail": "..."} envelope, never {"error": ...} or field-level DRF dicts.

6. IDS ARE PER-COMPANY; ALWAYS PASS Company-Code. Verified: sheet id 1 is 200 under JIVO_OIL and 404 {"detail":"No LabourCountSheet matches the given query."} under JIVO_MART; gate entry 322 likewise 404 as "No LabourGateEntry matches the given query." All five endpoints return 200 in all three companies (no 403 module gating here), but the data lives in JIVO_OIL — that is the physical factory, and its departments include the beverage lines ("production(beverages)", "Warehouse Beverage"), so beverage labour is recorded under JIVO_OIL, not JIVO_BEVERAGES.

7. NO PAGINATION ANYWHERE. All five endpoints return a bare array (or a bare object for sheet detail). There is no results/count/page envelope and no page/page_size param — a generated --page flag would be meaningless and misleading.

8. ENUMS. shift = DAY | NIGHT (uppercase, from the UI toggle). Sheet status = DRAFT | SUBMITTED | VERIFIED (plus is_holiday, which the UI renders as "Holiday" in place of the status). Audit action = CREATE_IN | UPDATE_IN | MARK_OUT | UNDO_OUT | DELETE | RESTORE. These came from the bundle; per the no-guessing rule none were probed against the API.

9. SHEETS AUTO-SUBMIT. `lock_at` is 18:30 IST on the work date for DAY and 06:30 IST the next morning for NIGHT (verified in live rows). Past lock_at a DRAFT auto-submits and `auto_submitted` flips true; is_editable and can_pull_back go false. So a "DRAFT" sheet is not necessarily still editable — read is_editable, don't infer from status.

10. gate_counted IS FED BY THE SHEET FLOW ONLY. sheet.gate_counted / variance are written by POST /labour-count/gate/out/, not by /labour-gate/ out batches. In every live row I pulled, gate_counted and variance are null. Do not present a sheet's variance as a gate reconciliation of the /labour-gate/ numbers — they are unrelated ledgers.

11. THE LABOUR MASTER IS A DIFFERENT THING — DO NOT JOIN. /person-gatein/labours/ (another domain) is a roster of NAMED individuals: 3 rows only (ABC, Renu, Dharmender kumar), belonging to contractors 2 and 3, essentially legacy/test data. /labour-gate/ counts ANONYMOUS heads against contractors 4, 6 and 7 — contractors that have zero named labourers in that roster. A LabourGateEntry has a `contractor` FK and no `labour` FK; the only shared master between the two systems is /person-gatein/contractors/ (7 contractors on OIL). So these are not the same people counted twice, and there is no key on which to join them. Person-gate-in is for individual passes; labour-gate is for daily headcount.

12. PERMISSIONS DIFFER FROM THE READ SURFACE. Django permissions are labour_gate.view_labourgateentry / can_record_labour_in / can_record_labour_out and labour_count.can_submit_labour_count / can_verify_labour_count. There is no labour_count.view_* permission — the labour-count reads are gated by the submit/verify permissions, so a read-only service account may be able to read /labour-gate/ and be refused on /labour-count/ even though both are GETs. My token had access to all five; a narrower operator token may not.

### Confidence & open questions

HIGH (verified live 2026-08-03) on all five GET endpoints and on the excluded write list. Each of the five was called against the live API and returned 200 with real rows or a documented empty array, in all three companies; each was additionally confirmed with an OPTIONS call that returned both the Allow header and the server's own view docstring, which independently corroborates the path, the required params and the business meaning. Required-param behaviour, optional filters (department, contractor, shift, from, to), the 400 error bodies, and the per-company 404 scoping were each reproduced live. GET /labour-gate/{id}/ was tested explicitly and returns 405, so I am certain it is write-only rather than dual-use — none of the five published paths is dual-use, which is unusual for this API and worth a reviewer's note.

VERIFIED vs INFERRED. Verified live: all paths, methods, status codes, required/optional params, error envelopes, response field sets, company scoping, the two row kinds in /labour-gate/, soft-deleted rows appearing in the list, shift being ignored on /labour-gate/, and board excluding DRAFT sheets. Inferred from the bundle only: the shift/status/audit-action enum VALUES (read out of the React UI, never probed — deliberately, per the no-guessing rule), and the 10-minute undo/restore window (a UI tooltip, not an API response).

WHAT I COULD NOT DETERMINE. (a) Whether /labour-count/sheet/history/ applies a server-side row cap at volume — only 4 sheets exist, so I could not exercise it. (b) Whether the labour-count flow is dormant by decision or simply not rolled out; I can only report the row counts and dates, not the intent. (c) Whether a narrower operator token can read /labour-count/ at all, given there is no view permission for that app — mine could, but that is one account. (d) Whether board's `contractor` filter matches on the sheet's items or on something else; it returned the expected single row for contractor=2 but there is only one populated sheet to test against.

SIDE-EFFECT RISK: I assess all five as clean, and the reasoning is not just "it's a GET". This domain puts its one get-or-create behind POST /labour-count/sheet/ensure/, whose own server docstring says "Get-or-create the DRAFT sheet" — the developers routed the creating path to POST deliberately. The two id-keyed reads I published (sheet detail, entry audit) return 404 rather than creating when handed an id from the wrong company, which is the opposite of the marketplace/settings behaviour. I used only ids observed in real payloads and enumerated no parameter values.

## Maintenance

*73 read commands · 46 write endpoints excluded*

The `/maintenance/` group is the factory's plant-engineering system — everything that keeps machines running and the site safe. It covers six workflows that share one asset register: (1) **Assets** — a hierarchy of plant/area/line/machine/component with categories, locations, departments, photos and documents (manuals, warranty, AMC); (2) **Work orders** — complaints and breakdowns raised against an asset, assigned to a technician, started, completed, approved and closed, with MTTR/MTBF and production-downtime tracking, and a link back to the production run that was stopped; (3) **Preventive maintenance** — PM plans on a frequency (daily…yearly), a checklist template per plan, and dated PM executions generated from those plans; (4) **Spares store** — a maintenance spare master with local stock plus a live SAP warehouse lookup, spare requests raised off a work order, issue/consume/return, and a movement ledger; (5) **Fire & safety store** — a parallel store for fire-safety equipment (extinguishers, hydrants, PPE) with its own categories, requests, movements, issue register, and a shift-wise fire inspection round (fire reports with per-equipment OK / NOT_OK / NEEDS_ATTENTION items and photos); plus safety violation types and the safety fines raised against workers; and (6) **Material indents and work permits** — a 6-step maintenance purchase demand (submit → review → approve → purchase → gate-in → receive into store) and a full permit-to-work system (hot work, height, confined space, etc.) with workers, hazards, PPE, isolations, approvals and renewals. There is also a dashboard, a 12-flavour report endpoint, an alerts feed and a QR/code scan lookup. Almost all of this is new since July: the baseline knew 21 endpoints, the module now exposes 72 readable ones. In practice **JIVO_OIL is the only company with real data** — Mart is completely empty and Beverages has one work order and one fire issue.

### Traps

1) NO PAGINATION ANYWHERE. Every maintenance list returns a bare JSON array. Verified decisively: GET /maintenance/material-indents/?page=2&page_size=1 returned all 17 rows. A generated --page/--page-size flag would be a silent lie on every endpoint in this group. Singleton endpoints (dashboard, options, reports, alerts, scan-lookup, spare-stock, every {id}/ route) return a bare object.

2) UNKNOWN QUERY PARAMS ARE SILENTLY IGNORED, NOT REJECTED. Verified: /maintenance/work-orders/?bogusparam=1 returned all 5 rows, HTTP 200. So a typo'd filter name produces a plausible-looking wrong answer with no error. The CLI must validate param names locally; it cannot rely on the API.

3) "ALL" IS A UI SENTINEL, NOT A SERVER VALUE. Every maintenance service wrapper strips undefined, "" and the literal string "ALL" before sending. A CLI that forwards --status ALL will send status=ALL, which the server will treat as a real status and return zero rows. Omit the param instead.

4) JIVO_OIL IS THE ONLY COMPANY WITH DATA. All 41 collection endpoints return HTTP 200 in all three companies — there is no module gating and no 403 anywhere in this group. But JIVO_MART is completely empty across every maintenance table, and JIVO_BEVERAGES has exactly two rows in the whole module (1 work order, 1 fire issue). Default the CLI to JIVO_OIL for maintenance questions, or an operator will conclude the plant has no assets.

5) TWO "404s" IN THE COMPANY MATRIX ARE LIVE ENDPOINTS, NOT DEAD ROUTES. /maintenance/scan/lookup/ and /maintenance/spares/stock/ show 404 in all three companies because they were probed with no key. Their bodies are application JSON ({"found":false,…} and {"detail":"Spare was not found for the selected code."}), not the HTML "Not Found" page an unrouted path returns. Both are real, required-param GET endpoints. Do not drop them as 404s.

6) A DRF 404 ON A DETAIL ROUTE PROVES GET IS ROUTED. I confirmed every {id}/ route in this group serves GET by checking that the response is a DRF {"detail":"No <Model> matches the given query."} 404 rather than a 405. A method that is genuinely not allowed returns 405 here — /maintenance/pm-plans/generate-due/ does exactly that. So "404 on an empty table" and "endpoint does not exist" are different findings.

7) THE BUNDLE'S METHOD ARRAYS UNDER-REPORT GET ON 11 PATHS. HARVEST.json lists asset-categories, asset-locations, asset-departments, spare-categories, fire-report-items, fire-report-photos, fire-report-attachments, material-indent-attachments, safety-fine-photos, work-permit-workers and work-permit-attachments as POST-only, because the UI only ever writes to them. All eleven return 200 on GET live. If the generator filters on the harvested methods array alone it will drop eleven working read endpoints.

8) 26 OF THE 41 COLLECTION PATHS ARE DUAL-USE. The same URL that lists also creates (GET+POST), and most {id}/ routes are GET+PUT or GET+PATCH+DELETE. Publish the GET, publish nothing about the verb, and keep the read-only guard at the HTTP-method layer, not the path layer.

9) FIVE ENDPOINTS THE WEB APP NEVER CALLS. /maintenance/spares/low-stock/, /maintenance/fire/low-stock/, /maintenance/spare-movements/, /maintenance/fire-movements/ and the excluded /maintenance/assets/{id}/qr/ are defined in the service layer with no consumer anywhere in the bundle. The four movement/low-stock ones are verified live and are genuinely useful (fire-movements returned 5 real ledger rows) — the CLI would be the only client reading them. That also means their filter params were never exercised by the UI; I verified movement_type and fire_item live on fire-movements and category on fire/low-stock, and the spare twins are inferred by symmetry.

10) FK FILTER NAMES ARE NOT UNIFORM AND ARE EASY TO GET BACKWARDS. fire-report-items filters by `report`; fire-report-photos filters by `item` (the checklist LINE, not the report); fire-report-attachments filters by `report`. safety-fine-photos uses `fine`, material-indent-attachments uses `indent`, work-permit-workers/attachments use `permit`, asset-photos/documents use `asset`, work-order-photos uses `work_order`, spare-requests and vendor-visits use `work_order`, spares uses `compatible_asset`, fire-movements uses `fire_item`.

11) FILTER VALUES THAT LOOK LIKE NAMES ARE INTEGER IDs. department, category, location, asset, violation_type, pm_plan, spare, fire_item, report, item, permit, fine, indent, work_order are all primary keys. Resolve them from /maintenance/options/ (which carries categories, locations, departments, org_departments, spare_categories, users, production_machines in full) — never string-match a name against a filter.

12) TWO DIFFERENT DEPARTMENT LISTS. /maintenance/asset-departments/ (2 rows in Oil) is maintenance's own department master and is what the `department` filter on assets/work-orders/dashboard/reports takes. /maintenance/options/.org_departments (18 rows) is the company-wide org chart used by safety fines. Mixing them returns zero rows with no error.

13) /maintenance/reports/ DEFAULTS TO TODAY. date_from and date_to both default to the current date, so a bare call returns a one-day report that will almost always be empty. Always pass an explicit range. The same path also serves a binary file download via export=csv|excel|pdf — that response is a blob, not JSON, and must not be piped through a JSON printer.

14) STATUS ENUMS ARE PER-ENTITY AND THE LABELS ARE NOT THE VALUES. Six separate status vocabularies live in this group (asset, work order, work permit, safety fine, material indent, spare/fire request, PM execution, fire report, fire issue, vendor visit). Material-indent values are especially misleading: SUBMITTED = "Submitted to Store", ISSUED = "Issued from Store", PENDING_APPROVAL = "Pending Purchase Approval", GATE_IN = "Arrived at Gate". Take the values from /maintenance/options/ and from the enums recorded per endpoint above, never from the *_display strings.

15) work_permits.permit_types IS AN ARRAY, THE FILTER IS SINGULAR. The record carries permit_types: ["GENERAL","HOT_WORK"]; the query param is permit_type (verified live). Same trap in reverse for anything that reads the record back.

16) THE OBVIOUS ADJACENT GROUP IS NOT MINE. /maintenance-gatein/gate-entries/... and /gate-core/maintenance-gate-entry/{id}/ contain the word "maintenance" but sit under different top-level segments and belong to the gate domain. Only /maintenance-gatein/gate-entries/maintenance/types/ was probed (200 in all three). Whoever owns the gate group must pick these up or they will fall through the cracks.

17) SIDE-EFFECT SCREENING RESULT. I checked every endpoint in this group against the get_or_create pattern. The only one I could not clear is /maintenance/assets/{id}/qr/ — flagged, not probed, and excluded. Two lookup-key endpoints that superficially fit the pattern are cleared by positive live evidence: /maintenance/scan/lookup/ returned {"found":false} for both an empty code and an observed real asset_code rather than creating anything, and /maintenance/spares/stock/ returns a DRF "not found" 404 on a miss. Everything else in the group is either a plain list, a plain detail retrieve, or a computed aggregate (dashboard/reports/alerts) with no key-based upsert shape.

## Marketplace — catalogue & reconciliation

*13 read commands · 8 write endpoints excluded*

This is the catalogue and reconciliation half of JIVO's Marketplace module — the cell that fulfils Flipkart/Amazon orders out of the Mayapuri e-com warehouse. The operator flow is: Upload an order sheet → Review & map → Warehouse → Issue & receive → Pack → Dispatch → Gate; this domain owns the first two steps plus the after-the-fact reconciliation. An order sheet uploaded from the portal becomes a **batch** (the "Recent imports" list): the system parses each row, matches the line to a **SKU mapping**, and explodes it into a consolidated stock list of SAP finished goods and packing material to be issued by the warehouse. A **SKU mapping** ties a marketplace listing (Flipkart FSN first, marketplace SKU as fallback) either to one SAP finished-good item (`sku_type=RAW`) or to a **combo** (`sku_type=COMBO`) — a multi-pack listing that ships as several SAP items, e.g. "Extra-Virgin-5L+200ml" = FG0000074 + FG0000381. Combos carry components typed FG (finished good) or PM (packing material), each with a quantity, a UOM, and optional interchangeable alternatives the operator picks at delivery-note time. `sap-items` is the type-ahead an operator uses to find the SAP item code when creating a mapping. **Warehouse insights** is the issued-vs-dispatched scoreboard the warehouse desk reads, and **reconciliation** is the per-order-item deviation report: portal quantity vs outward vs inward, flagging where what the portal ordered, what left the godown and what came back do not agree. Everything here is JIVO_MART only — the marketplace module is not enabled for the Oil or Beverages company units.

### Traps

1) PHANTOM FILTERS ON sku-mappings — the biggest correctness trap. The harvest credits /marketplace/sku-mappings/ with query params sku_type, is_active, marketplace_sku, fg_item_code and combo. They are POST-body fields that the extraction lens promoted to query params, and the server IGNORES all of them. Proved live, not assumed: the table holds 208 COMBO and 5 RAW rows, yet ?sku_type=COMBO returns all 213; all 213 rows are active, yet ?is_active=false returns all 213; ?marketplace_sku=BOTGZ9ZPVHFX8YYG returns all 213. Emitting those flags ships a command that silently lies. Only `channel` filters.

2) THE ONLY REAL FILTER IS channel, AND IT IS OPTIONAL EVERYWHERE I PUBLISH. Verified honoured on sku-mappings, combos, batches, reconciliation and warehouse-insights (AMAZON returns empty/zero on each). It is REQUIRED on exactly one published path: /marketplace/reports/reconciliation/export.csv (400 MARKETPLACE_ERROR without it). Enum is FLIPKART|AMAZON — those are the only two values in the UI selector and the only two in live data. Never enumerate other channel values against this API; that is precisely what created six junk /marketplace/settings/ rows on 2026-08-03.

3) RECONCILIATION DATE FILTERS ARE BROKEN UPSTREAM. GET /marketplace/reconciliation/?from_date=… → HTTP 500, ?to_date=… → HTTP 500, both → HTTP 500 (Django HTML error page, not a JSON envelope). The app's own Reconciliation page exposes those pickers, so this is broken for humans too. The date-scoped path that WORKS is the CSV export, and it uses different param names: `from`/`to`, not `from_date`/`to_date`. Publish --from/--to on reconciliation-export-csv only; publish no date flags on the JSON endpoint.

4) TWO PATHS HAVE NO TRAILING SLASH AND END IN .csv — /marketplace/batches/{id}/issuance.csv and /marketplace/reports/reconciliation/export.csv. A generator that normalises every path to end in '/' will 404 both. They also return text/csv, not JSON, so --json is meaningless and the body must be streamed or written to a file.

5) DO NOT ASSUME DRF PAGINATION. Every endpoint in this domain returns either a bare array (sku-mappings, combos, sap-items, batches, warehouses) or a bare object (batch detail, stock-list, variants, reconciliation, warehouse-insights). Not one carries results/count/next/previous. --page/--page-size would be dead flags on all of them. Reconciliation in particular returns its ENTIRE row set inside one object — ~884 KB in 6–8 s — so it needs a generous timeout, not a pager.

6) sap-items IS CAPPED AT 30 AND NEEDS ≥2 CHARACTERS. ?search=OLIVE, ?search=OL and ?search=PCS each returned exactly 30; ?search=O returned []; no search at all returns 200 [] rather than a 400. It is a picker, not an item master — a command described as "search SAP items" will be read as exhaustive and will quietly drop results. There is no limit/offset to raise the cap.

7) sku_type 'RAW' DOES NOT MEAN RAW MATERIAL. In this module RAW = "this listing maps directly to one SAP finished good" (the UI labels it "SAP item" / "Direct finished good"), versus COMBO = "ships as a multi-item kit". Given that JIVO's SAP has genuine RM item codes, a description saying "raw" will be misread by an accounts or factory operator. Relatedly, 208 of 213 mappings are COMBO with fg_item_code="" — any table column that prints only fg_item_code is blank for 98% of rows; fall back to combo_code/combo_name.

8) warehouse-insights `in_packing` GOES NEGATIVE. Live values include −198, −500, −381 per item, because `dispatched` counts all-time while `issued` counts only what passed through the issue-request flow (totals: issued 758 vs dispatched 3,978). It is a bookkeeping delta, not stock on hand. Present it as "issued minus dispatched" and never as inventory.

9) COMPANY SCOPING: every path here is 403 on JIVO_OIL and JIVO_BEVERAGES with {"code":"WRONG_COMPANY","error":"The marketplace module is not enabled for this company unit."} — say "module not enabled for this company", never "no permission" and never "no data". It could be enabled elsewhere later, so the commands should stay registered and let the 403 speak.

10) DETAIL ROUTES ARE WRITE-ONLY, WHICH IS COUNTERINTUITIVE FOR A DRF API. /marketplace/combos/3/, /marketplace/sku-mappings/111/ and /marketplace/warehouses/1/ all return 405 "Method GET not allowed" — verified live against ids observed in real payloads. There is no way to fetch a single mapping, combo or warehouse; the CLI must fetch the list and filter client-side. Only the batch detail route exposes GET.

11) unmapped_skus IS THE BLOCKER, NOT A FOOTNOTE. In /marketplace/batches/{id}/stock-list/, a non-empty unmapped_skus means the batch cannot be sent to the warehouse at all ("Resolve unmapped SKUs first"). A command that prints the lines table and hides that array will show an operator a stock list they cannot act on.

### Gone or broken since July

- For the reviewer's ledger, the one thing that is broken RIGHT NOW rather than lost: GET /marketplace/reconciliation/ with from_date or to_date → HTTP 500. It is new-and-broken, not regressed, since the endpoint did not exist in July.

### Confidence & open questions

VERIFIED LIVE BY ME (my own serial GETs against JIVO_MART on 2026-08-03), highest confidence: every published endpoint returned 200 and I read the real payload — sku-mappings (213 rows), combos (173), sap-items (30-cap, 2-char minimum), batches (23 rows, ids 29–51), batches/51/, batches/51/stock-list/, batches/51/variants/, batches/51/issuance.csv (headers + CSV columns), reconciliation (both unfiltered and channel-scoped), reports/reconciliation/export.csv (with and without dates, and the 400 without channel), warehouse-insights (FLIPKART and AMAZON), warehouses. ## Marketplace — orders, dispatch & returns

*27 read commands · 28 write endpoints excluded*

This is JIVO's e-commerce fulfilment cell — the desk that turns a Flipkart/Amazon seller-portal order sheet into stock leaving the building with a SAP delivery note against it. The app's own flow bar names seven steps: (1) Upload the order sheet, (2) Review & map SKUs, (3) Warehouse, (4) Issue & receive, (5) Pack, (6) Dispatch, (7) Gate. An uploaded sheet becomes a "batch"; the batch is exploded into a consolidated stock list of SAP finished-good (FG) and packing-material (PM) items; a warehouse issue request (MPIR-nn) is raised, reviewed, issued and received; parcels are scanned out against the marketplace Tracking ID in Outward; a single SAP delivery note is then cut for all confirmed dispatches; and Gate approves the sheet's parcels out of the premises. Returns come back through the same door in reverse — scan the returned tracking ID, set each item's condition, submit a Return Note. Everything is per channel and Flipkart and Amazon are kept completely separate (the UI says so verbatim). Volume as of 2026-08-03: 2,171 orders (2,129 Flipkart + 42 Amazon), 2,130 dispatches, 1 return, 51 import batches. Note the words differ between screens for the same object: an import "batch", a dispatch "sheet", a gate "sheet" and a delivery-note "sheet" are all the same row — batch_id and sheet id are interchangeable.

### Traps

1) MODULE GATING, NOT PERMISSIONS. Every marketplace path returns 403 {"code":"WRONG_COMPANY","error":"The marketplace module is not enabled for this company unit."} on JIVO_OIL and JIVO_BEVERAGES. The frontend agrees - the marketplace nav module is declared companies:["JIVO_MART"]. Say "the marketplace module is not enabled for this company", never "no permission" and never "no data". It could be switched on elsewhere later.

2) /marketplace/settings/ MUST NOT BE PUBLISHED. GET with a channel value is a get_or_create and on 2026-08-03 it created six live rows (AMAZON, MEESHO, JIOMART, BLINKIT, ZEPTO and a junk INVALID_XYZ) merely by being read. It sits in the same domain as my endpoints and is the obvious thing a generator would sweep up. No CLI command, no MCP tool, no "just to check the config" call. I did not touch it.

3) NEVER INVENT A CHANNEL. The only channel values ever observed are FLIPKART and AMAZON - those are the two the UI offers and the only two in data. Enumerating channels is exactly what created the junk settings rows. A CLI --channel flag must be a closed enum of FLIPKART|AMAZON, not free text.

4) FOUR PATHS ARE DUAL-USE (GET + a write verb on the SAME URL): /marketplace/dispatches/ (GET+POST), /marketplace/returns/ (GET+POST), /marketplace/issue-requests/ (GET+POST), /marketplace/delivery-notes/reconcile/ (GET+POST, and its POST finalises SAP delivery notes). Filtering on an is_mutation flag would have let all four through as "safe". Only the GET is published for each.

5) MOST OF THIS DOMAIN IS *NOT* DRF-PAGINATED. Only five of my endpoints return an envelope: orders, dispatches, returns, packing/queue (results+count+page+page_size+total_pages+next+previous) - and note next/previous are BOOLEANS, not URLs, so a generic "follow next" pager will break. Everything else (batches, issue-requests) is a bare array, or a bare object with a named key (sheets/notes/orders/items/lines). Do not emit --page/--page-size on those.

6) page_size IS CAPPED AT 100. Requesting 500 silently returns 100 and echoes page_size:100. A command that assumes it got everything will under-report.

7) FILTER PARAMS ARE SILENTLY IGNORED, NOT REJECTED. Verified live: `search` works on /marketplace/orders/ but is ignored on /marketplace/dispatches/, /marketplace/returns/ and /marketplace/packing/queue/ (row count unchanged); `status` works on orders, dispatches and returns but is ignored on packing/queue; `order_id`, `from` and `to` are ignored on /marketplace/orders/. An unrecognised *value* is equally silent - status=ZZZ_NOT_A_STATUS returns count 0, not a 400. So a typo reads as "no such orders". Only publish the params proved to work per endpoint.

8) `search` ON ORDERS MATCHES order_id ONLY. Verified: the full order id returns 1 row, a prefix (OD3382409) returns 1 row, but "Hassan" and "Pomace" return 0 against rows containing exactly those strings. Do not describe it as a general search.

9) THE SAME ROW HAS FOUR NAMES. An import "batch", a dispatch "sheet", a gate "batch_id" and a delivery-note "sheet" are the same object with the same id. /marketplace/gate/{id}/ and /marketplace/dispatches/board/{id}/ both take that BATCH id - passing a dispatch_id there silently returns the wrong sheet or 404.

10) CHANNEL IS REQUIRED ON SIX ENDPOINTS AND OPTIONAL ON THE REST. Required (400 "channel is required." without it): /delivery-notes/sheets/, /delivery-notes/summary/, /dispatches/sheets/, /dispatches/orders-in-range/, /dispatches/board/{id}/, /gate/queue/, /gate/{id}/, and /orders/resolve/ (which also needs order_id). Optional filter (returns all channels when omitted): /orders/, /dispatches/, /returns/, /batches/, /issue-requests/, /packing/queue/, /packing/summary/, /delivery-notes/posted/, /delivery-notes/reconcile/.

11) orders-in-range FILTERS ON SHEET UPLOAD DATE, NOT ORDER DATE. Verified: from=2026-08-01 returned an order dated 2026-07-22 because its sheet was uploaded on the 1st. Anyone reading it as "orders placed in this window" will report the wrong number.

12) FOUR ERROR ENVELOPES, and this domain uses a fifth-party one consistently: {"code":"MARKETPLACE_ERROR","error":"..."} for missing params and {"code":"WRONG_COMPANY","error":"..."} for module gating. The error string names the missing param verbatim - surface it rather than a generic "bad request".

13) TWO PATHS END IN .csv WITH NO TRAILING SLASH (/marketplace/batches/{id}/issuance.csv, /marketplace/delivery-notes/{id}/export.csv, /marketplace/reports/{slug}/export.csv). Adding the trailing slash the rest of the API uses gets a 301. These return text/csv - the client must not JSON-decode them.

14) dn-export-csv TAKES doc_entry, NOT doc_num. The UI passes note.doc_entry (12259); the file is then named after doc_num (1507264762). Feeding doc_num will 404.

15) THE PACKING SUB-DOMAIN IS BACKEND-LIVE BUT UI-DEAD IN THIS BUILD. No /marketplace/packing route is registered, the flow bar's step-5 "Pack" link goes nowhere, and no React hook calls packing/queue or packing/summary - which is why packing_status is null on all 336 queue rows. Same for /marketplace/orders/ and /marketplace/orders/resolve/: both have query keys but no hook. The CLI will therefore expose data the web app cannot currently show. That is genuinely useful, but do not describe packing_status as a workflow state that is being maintained.

16) RETURNS AND ISSUE REQUESTS ARE ALMOST EMPTY. One return and one issue request exist system-wide on 2026-08-03. An answer built on them is anecdote, not a trend.

17) QUANTITIES HERE ARE PER SAP ITEM CODE, IN PCS/CARTON UNITS (e.g. "MUSTARD KACCHI GHANI 5 LTR 4 PCS", uom PCS) - they are not litres and not bottles. Do not convert to tonnes without resolving the pack size from the item master.

## Person gate-in — visitors, labour, contractors

*20 read commands · 7 write endpoints excluded*

This is the factory's people register at the gate — who walked into the plant, when, through which gate, why, and whether they have walked back out. It covers two kinds of person: **visitors** (outsiders coming for a meeting, a service call, a delivery discussion) and **labours** (contract workers who belong to a named **contractor**). Security opens an "entry" at a gate, and closes it when the person leaves; anyone with an open entry is "currently inside". Around that sit four small master lists the gate desk maintains itself — visitors, labours, contractors, and the gates themselves — plus a "person type" lookup (1 = visitor, 2 = labour). The dashboard is the security supervisor's screen: how many people are inside right now, split visitor/labour, how many have been inside unusually long, today's ins and outs, and a gate-wise headcount. Two history views answer "has this person been here before, and are they inside now", and a contractor view answers "which of my gang are in the plant at this moment". In practice today the module is used almost entirely for visitors: 287 entries since 19-Feb-2026, of which exactly one is a labour entry, through a single gate called "Front gate". Note this is a plant-wide register, not a company ledger — it returns identical data whichever of the three companies you ask as.

### Traps

1. **THIS DOMAIN IS NOT COMPANY-SCOPED — the biggest trap.** Every person-gatein endpoint returns byte-identical data for JIVO_MART, JIVO_OIL and JIVO_BEVERAGES. Verified two ways: the probe byte counts match exactly (visitors 39612, entries 187039, contractors 1064, dashboard 7012, gates 63, labours 444, person-types 86), and I md5'd /person-gatein/visitors/ under all three company codes — 3b7c75d4496d7c095bf71b31e7a397fc every time. This is NOT the header being ignored: a control request to /po/warehouses/ under the same token returned different md5s and different sizes (2106 vs 3113 bytes) for MART vs OIL, proving Company-Code is honoured elsewhere. So this is one shared plant gate register. A --company flag here must be a no-op, and no answer from this domain may ever be labelled "Mart's visitors" or "Oil's labour" — it is the whole plant's.

2. **`from_date` / `to_date` on `/person-gatein/entries/` are silently ignored.** The SPA's All Entries page ships a date-range picker and sends them; the backend drops them. Verified: `?from_date=2026-08-01` returned all 287 rows with min entry_time 2026-02-19, and `?to_date=2026-02-20` returned all 287 with max entry_time 2026-08-03. Publishing --from-date/--to-date on this command would produce confidently wrong answers to "how many visitors came last week". Filter on entry_time client-side. The SAME two params on `/person-gatein/dashboard/` DO work (they drive the `range` block only — verified 75 entries / 74 exits for July vs 1/1 today), so the flags are legitimate there and forbidden here.

3. **Three more dead filters.** `?search=` on /visitors/ (197 rows in, 197 rows out — verified), `?search=` on /labours/ and `?contractor=` on /labours/ (returned labours of contractors 2 AND 3 when asked for contractor 2 — verified). Only `/person-gatein/entries/search/?q=` actually searches server-side. For one contractor's gang use /person-gatein/contractor/{id}/labours-status/.

4. **`status` is unvalidated.** `?status=BOGUS` returns `{"count":0,"results":[]}`, not a 400. A typo is indistinguishable from a genuinely empty result. Valid values are exactly IN, OUT, CANCELLED (live tally: 0 / 284 / 3 = 287).

5. **`person_type` is a number, not a word.** `?person_type=1` = visitor, `=2` = labour, matching the SPA's frozen PERSON_TYPE constant and the live /person-types/ table. Passing `person_type=visitor` will silently return zero rows (see gotcha 4).

6. **Singular vs plural path segments — four routes break naive normalisation.** Masters are plural (`/visitors/`, `/labours/`, `/contractors/`, `/entries/`) but the derived views are singular (`/visitor/{id}/history/`, `/labour/{id}/history/`, `/contractor/{id}/labours-status/`, `/entry/{id}/`, `/entry/inside/`). Any generator that "corrects" these to match its sibling will 404.

7. **Four different response envelopes inside one small domain.** Bare array (6 endpoints), bare object (11), `{count, results}` with no next/previous (1: /entries/), and `{query, count, results}` (1: /entries/search/). `/entries/` count always equals len(results) — it is a filtered total, NOT a pagination cursor. `page` and `page_size` are accepted and ignored (verified: ?page_size=5 and ?page=2 both returned all 287). Do not generate --page/--page-size anywhere in this domain.

8. **`/person-gatein/entries/count/` is a 404 in all three companies** and returns an HTML error page, not JSON — so a JSON-assuming error handler will raise a parse error instead of reporting a clean 404. The SPA's getEntryCounts() is dead code aimed at a route that was never implemented. Exclude it.

9. **The bundle undercounts GET support on three master detail routes.** The SPA's api module defines only updateX/deleteX for `/contractors/{id}/`, `/gates/{id}/` and `/person-types/{id}/`, so a methods array derived from the bundle reads [PUT, DELETE] and the endpoint looks write-only. All three return live 200 on GET — I probed each. Any bundle-derived exclusion here loses three legitimate read commands; conversely, do not assume the reverse (that a bundle-only path is safe).

10. **Response objects with the same-looking name are not the same object.** `contractors` uses `contractor_name`, every other master uses `name`. `/entry/{id}/` adds a `duration` block the list serializer lacks. `visitor/{id}/history/` returns `total_visits` while `labour/{id}/history/` returns `total_entries`. The labour rows inside `contractor/{id}/labours-status/` carry `is_inside` and omit `is_active`/`contractor`, unlike `/labours/` rows. `check-status` is outright polymorphic (visitor branch has `blacklisted`; labour branch has `is_active` + `permit_valid` + `permit_valid_till`). One shared model across these will drop fields.

11. **`name_snapshot` is frozen at entry time.** Entries store the name as typed at the gate, alongside a `visitor`/`labour` FK. Exactly one of those two FKs is non-null and that is how visitor and labour entries are told apart. If a master record is later renamed, historic entries keep the old name — join on the FK when you need the current one.

12. **Do not confuse this with `/labour-gate/`.** That is a separate module (`labourGate.api` chunk, base `/labour-gate`) doing per-day headcount tallies with in/out counts and an audit trail. person-gatein tracks *named individuals*; labour-gate tracks *numbers*. Given the data below, an operator asking "how many labourers were in the plant" is almost certainly asking about /labour-gate/, not this domain.

13. **The labour half of this module is effectively unused in production.** Live today: 287 entries since 19-Feb-2026, of which 286 are visitors and exactly ONE is a labour entry (id 12, 26-Feb-2026). Three labours, seven contractors, one gate. Any labour or contractor analytics built on person-gatein will look empty and be misleading; the visitor register is the part that is genuinely in use.

14. **GET-mutation risk in this domain: none found, and that is a measurement not an assumption.** The one endpoint that fits the get_or_create profile — `/person-gatein/check-status/`, lookup key in, single object out — was probed only with IDs observed in real payloads (visitor=200, labour=2) and bracketed by row-count reads: entries 287→287 and visitors 197→197 across two calls. Nothing was created. Behaviour with a novel id remains untested by design, so the CLI must pass through ids the operator already holds and must never enumerate.

## Platform — accounts, notifications, OMS bridge, AI

*11 read commands · 11 write endpoints excluded*

The "platform" group is the plumbing the rest of the factory app sits on: who you are, who else exists, what the app tells people, and the one hand-off point with JIVO's separate order system. /accounts/ answers "who am I, what am I allowed to do, who else is on the system, and what departments exist" — the department list (IT, Ecom, Account, Store, Dock, Quality, Boiling Floor 1, Warehouse Basement, Fire, production(oil), production(beverages), …) is the same master list used by attendance, labour-count and gate-in forms. /notifications/ is the in-app + phone (Firebase push) alert stream: every gate entry, QC approval, GRPO posting, dispatch booking, material indent and returnable-item event raises a notification against one of 61 typed events, and an operator can read the feed, the unread badge, and which event types their account subscribes to. /ai/ is a single in-app LLM assistant used mostly to debug barcode/label problems ("Why is Generate Boxes not working?") — it is POST-only and therefore contributes no commands. /oms/ is the bridge to JIVO's separate OMS at oms.jivo.in: OMS pushes a ready-to-post SAP invoice payload into the factory, a warehouse person checks it against real physical stock and batch availability, then approves or rejects it. This is NOT a live proxy of oms.jivo.in — the factory runs its own Django `oms` app (permissions oms.view_invoice / oms.approve_invoice) with its own invoice, history and audit tables, so factory `oms invoices` and the separate `oms-cli` answer different questions and can disagree. Reading side: the pending queue per warehouse, the count badge, the invoice's snapshot history and the factory-side approve/reject audit trail. The approve/reject action itself is a PATCH and is excluded.

### Traps

1) whs is REQUIRED on both /oms/ reads and the two endpoints report the same failure in DIFFERENT envelopes: the list gives DRF field-level {"whs":["This field is required."]} while pending-count gives {"detail":"whs (warehouse) is required"}. A command that only parses one style will print an empty error for the other.
2) whs values are SAP warehouse codes and must be taken from GET /po/warehouses/ (31 live in MART: 01, BH-FG, BH-FGM, BH-FK, BH-GR, BH-GRM, BH-INT, BH-JM, BH-LR, BH-PF, DL-EC, DL-FA, DL-FG, DL-GG, DL-GR, DL-INT, DL-ISD, DL-IT, DL-MP, DL-OT, DP-DL, DP-HR, DP-PB, FBF-HR, GM-HR, GP-ECM, GP-FGM, GP-GRM, KT-FBF, KT-FG, PB-FG). Never let a command guess or sweep codes.
3) The whole /oms/ group IGNORES Company-Code. Verified: whs=BH-PF returns the identical two invoices under JIVO_MART, JIVO_OIL and JIVO_BEVERAGES. A --company flag on these commands would be a lie; the row's own `branch` field ("OIL") is the SAP/OMS branch and is unrelated to the header. Same for /accounts/me/, /accounts/users/ and /accounts/departments/ — byte-identical across all three companies.
4) But /notifications/ IS company-scoped (MART 297, OIL 6212, BEVERAGES 792) while /notifications/{id}/ is NOT — an OIL notification id fetched with a MART header returned 200 with the OIL row. So --company changes the list and silently does nothing on the detail. Document that asymmetry or an operator will think the detail is filtered.
5) Unknown query params are SILENTLY IGNORED on /notifications/ — notification_type=GENERAL_ANNOUNCEMENT and bogusparam=1 both returned the full unfiltered 297. A generated --type flag would look like it worked and quietly return everything. Only is_read, limit, offset, page, page_size are real.
6) The /notifications/ envelope is a FOURTH shape, not either DRF style in the brief: results + count + total_count + unread_count + page + page_size + limit + offset, with NO next/previous and NO total_pages. page/page_size and offset/limit are two names for one window (page=2&page_size=3 → limit 3, offset 3); emitting both flag pairs invites contradictory input. count/total_count are the TOTAL matching rows, not rows-in-page; unread_count is account-wide and ignores the is_read filter. Every other endpoint in this group is a bare array or bare object with no pagination at all.
7) The OMS approval queue is empty almost everywhere — 29 of 31 MART warehouses returned []. A command that defaults to the "main" warehouse (DL-MP) will always look broken. The live data sits on BH-PF. Tell the operator to check the FG production warehouse, and treat [] as normal, not as an error.
8) /oms/invoices/ status enum: PENDING | APPROVED | EDITED | REJECTED are the filterable values (the UI tabs actually show only PENDING/APPROVED/REJECTED and hide EDITED). A row can additionally hold ERROR, POSTED_TO_SAP or CL_RAISED — these exist in the status display map but were never sent as filters by the UI, so do not publish them as accepted --status values without proof.
9) /accounts/users/ is NOT company-filtered despite the UI caching it as "company-users" and the Send-Notification page saying "users in your company" — same 90 ids under MART and OIL. Do not describe it as a per-company roster.
10) /accounts/me/ permissions is a flat 1325-item Django perm list on a superuser and is identical under every Company-Code; per-company information lives only in companies[].role. Never derive "what can this person do in Mart" from the permissions array.
11) Two dual-use URLs in this group — /accounts/departments/ (GET+POST create) and /notifications/preferences/ (GET+POST toggle). Filter on the methods array, not on any is_mutation/write_only flag: both endpoints have write_only=false and is_mutation=false in HARVEST, so a flag-based filter would happily admit their POSTs.
12) /oms/invoices/{id}/history/ and /oms/invoices/{id}/audit/ are different records with confusingly similar names: history = the OMS-side submission snapshots (created_by is a username STRING like "mansi"), audit = factory-side approve/reject decisions (decision, acted_by_name). The queue row's own created_by is an INTEGER user id. Three different "who" fields, three different types.
13) The factory /oms/ endpoints do NOT proxy oms.jivo.in. Factory runs its own Django `oms` app (perms oms.view_invoice, oms.approve_invoice) with local invoice/history/audit tables that OMS pushes into. Do not describe a factory `oms` command as "the OMS system" — the separate oms-cli hits oms.jivo.in and can legitimately disagree. In particular factory's history route works, while the July oms-cli survey found oms.jivo.in's own /api/invoice/history/{id}/ missing.
14) Django APPEND_SLASH is on: every path in this group ends in a slash and must be emitted verbatim; dropping it costs a 301.

## Production execution

*51 read commands · 43 write endpoints excluded*

This is the factory's shop-floor execution system (MES) for the Bhakharpur plant — it is where a production run is born, tracked minute by minute, and costed. An operator sets up master data once (lines like "10 Head", "6 Head", "Clear Pack", "Pouch Machine", "Sidel"; breakdown categories like Machine / PM Short / RM Short / Labour; line-configs — since 2026-08-05 these are **named presets, several per line** ('1 LTR', '250ml', 'Hitech'), each carrying a rated speed in bottles/hr and an OPTIONAL SKU, maintained on the Line Management screen and picked by name when a run starts; and cost rates per case/day/month), then each shift a supervisor creates a run against a SKU, gets a line clearance signed off by QA, starts production, logs stoppages as they happen, records material consumption, wastage, manpower and utility usage, and completes the run. Everything downstream — OEE, downtime Pareto, cost per case, waste trend, monthly summary — is computed from those runs. A second half of this domain is the SAP bridge: it reads SAP production orders, item master and BOMs live out of HANA so a run can be raised against a real SAP order, and it runs three reconciliations that compare what the app recorded against what SAP actually posted (production received into BH-PF, material issued into BH-PC, scrap moved into BH-WST) — this is the module that catches feeder breakages. Data lives in JIVO_OIL (106 runs, 7 lines, 94 clearances, 67 waste logs) and JIVO_BEVERAGES (7 runs, 2 lines); JIVO_MART is routed and enabled but has zero rows because Mart is a trading company with no plant. The whole domain is 94 bundle paths of which 53 accept GET; 41 are pure write endpoints (start/stop production, approvals, deletes) and are excluded.

### Traps

1. `line` vs `line_id` — THE trap. The list endpoints (/runs/, /line-clearance/, /line-configs/, /cost-rates/, /machines/) take **line_id**. The analytics reports (oee, oee-trend, cost-analysis, resource-consumption, waste-trend, downtime-pareto, monthly-summary, costs/analytics, the three reconciliations) take **line**. Verified live on JIVO_OIL: /reports/analytics/oee/?line=3 → 14 runs / 9,322 cases; ?line_id=3 → 45 runs / 33,071 cases, i.e. line_id is SILENTLY IGNORED and you get plant-wide numbers with no error. A generated command that guesses the wrong name returns a plausible, wrong answer.

2. Not every analytics report accepts `line` at all. Verified live by byte-comparing filtered vs unfiltered payloads: `line` IS honoured by oee, oee-trend, cost-analysis, resource-consumption, waste-trend, downtime-pareto, monthly-summary and costs/analytics; it is IGNORED by reports/analytics/ (base), reports/analytics/downtime/, reports/analytics/waste/ and reports/analytics/plan-vs-production/. Do not expose a --line flag on those four.

3. recon-material with `line` produces a fake mismatch. Verified live (OIL, 2026-07-30..08-01): the filter narrows the app side only, leaving sap_issued at its full 1,083,759, so difference_pct swings from -14.6% to -78.4%. Same risk applies to the other two reconciliations.

4. monthly-summary ignores date_from/date_to entirely — verified live, the payload is byte-identical with and without them. It takes `year` (+ optional `line`).

5. Four required params, each with a different error envelope, all confirmed live in all three companies: `line_id` for line-configs/auto-fill → {"error":"line_id is required"}; `sap_doc_entry` for procurement-vs-planned → {"error":"sap_doc_entry is required"}; `date` for reports/daily-production → {"detail":"date query parameter is required."}; `item_code` for sap/bom → {"detail":"item_code query parameter is required."}. Two envelope styles ({"error"} and {"detail"}) inside one domain.

6. sap/items has a hidden required param and a hard cap. With no `search` it returns 200 [] rather than a 400; with any broad term it returns exactly 50 rows ('COLD PRESS' 50, 'LTR' 50, 'OLIVE' 50, 'ZZZZ' 0). There is no paging param — it is a type-ahead, never an export.

7. No pagination anywhere in this domain. All 51 endpoints return either a bare JSON array or a bare JSON object. Not one returns a DRF results/count/next envelope. A generated --page/--page-size flag would be dead everywhere here. The only size control is production-movement's `limit` (default 500), which silently truncates and is echoed in meta.limit.

8. DocEntry is not DocNum. sap-order-detail keys on SAP DocEntry (2650), while the number printed on the order and shown in the UI dropdown is DocNum (225026669). An operator will quote DocNum.

9. sap/orders returns only OPEN orders. Verified: every one of the 31 OIL rows has Status='R', DocEntry 2650→12778, StartDates Feb-2025 → Aug-2026. It is the open backlog, not history.

10. sap/bom PlannedQty is PER UNIT; sap-order-detail components PlannedQty is FOR THE WHOLE ORDER. Same field name, 1000× different meaning.

11. Quantities and units. Run/production figures are in CASES (total_production, produced_qty, app_qty). SAP movement and reconciliation SAP columns are in the SAP inventory UOM (pieces for FG). recon-production bridges the two by parsing the pack size out of the SKU NAME ('20 PCS' → ÷20) — a renamed SKU breaks the match. Waste quantities are in each material's own UOM (PCS for bottles/caps/labels, GMS for shrink/BOPP), so waste-trend's summary.total_waste_qty adds PCS to GMS and is meaningless; report by_material instead.

12. Empty masters distort three reports. /machines/, /checklist-templates/ and /machine-checklists/ are 200-with-zero-rows in ALL THREE companies. Consequence: downtime-pareto.by_machine is always a single "Unknown" bucket, and machine-level downtime cannot be answered from this API today.

13. OEE became usable on 2026-08-05 — **this entry said the opposite until 2026-08-11, and repeating the old version is now a wrong answer.** The original finding was correct when written (2026-08-03): performance = actual ÷ (rated_speed × running hours), rated_speed comes from line-configs, JIVO_OIL had ZERO line-configs, so performance read ~1% and OEE 0.4-2.2% — an input problem, not a plant problem. The plant then filled the gap: the new **Line Management** screen (`/production/execution/line-management`) was built for exactly this, and on 2026-08-05 eleven configs were created across five OIL lines (10 Head 2100/1260/900 b/hr for 1/2/5 LTR, 6 Head 1080/720/600, Clear Pack 4800/3000, JP Machine 5400, Pouch Machine 1800/2400). Re-measured live 2026-08-11 on JIVO_OIL: **88 of 90 runs now return a non-zero performance, median performance 48.8%, median OEE 46.2%, 43 runs above 50%.** Availability still reads 95.7% plant-wide. Two caveats before quoting OEE as fact: the per-run spread is wide (13.5%-73.2% on 2026-08-10 alone), which may be genuine product/line variation or may be operators picking the wrong named config for the run; and the figure is only as good as the rated speed somebody typed into Line Management. Quote it as an operational indicator, not an audited number.

14. plan-vs-production reads ~10% achievement for the same reason in reverse: every observed run has sap_doc_entry null, so actual production is never credited to the SAP order it belongs to.

15. Two different "running minutes". downtime-pareto.summary.total_running_minutes (132,278 for OIL) and reports/analytics/oee's total_running_minutes (34,911) are computed on different bases. Never mix them in one answer.

16. downtime groups by RAW free-text reason, which on the Oil lines is unnormalised Hinglish — "sticker issue", "sticker", "sticker nahi hai", "STICKER CHAJ", "sticker change" are five buckets for one cause. Use downtime-pareto (grouped by the controlled category) for any rollup.

17. Reconciliation defaults to TODAY. Call recon-wastage with no dates on a quiet day and it returns status MATCHED with all zeros — a false all-clear. Always force a date range.

18. Breakdown-category IDs differ per company for the same name (Labour = 1 in OIL, 5 in BEVERAGES). Never hard-code a category id.

19. JIVO_MART is enabled and routed, not gated. Every production-execution endpoint returns 200 on JIVO_MART with empty data (Mart is a trading company with no plant). This is NOT the marketplace-style 403 module gate, and it is NOT missing permission — say "no production data in this company", never "not enabled".

20. Cost figures are SAP LastPurPrc × BOM quantity, not actual issue cost — stated verbatim in the cost line's own `note` field ("5 BOM item(s) × LastPurPrc"). Many runs also carry a non-zero total_cost against produced_qty 0, which poisons any average per-case figure.

## Production planning, SAP bridge & POs

*19 read commands · 6 write endpoints excluded*

This corner of the factory app answers one question: can we actually build what SAP says we are going to build, and what do we have to buy to close the gap. The "SAP Material Plan" screen (web route /dashboards/sap-plan) pulls every still-open production order out of that company's SAP HANA database, explodes each one against its BOM, and compares each component's requirement against stock on hand, stock already committed and stock on order — so an operator sees, per order, how many of its components are short, and per component, how much to purchase. Three views feed it: a one-row-per-order SKU summary, the same orders with every BOM line nested, and a procurement roll-up that aggregates shortfall by component with a suggested purchase quantity and the production orders driving it. The purchase-order side (/po/) is the vendor-facing half: the SAP vendor master, the SAP warehouse list, and open (not-yet-fully-received) purchase orders with per-line ordered / received / remaining quantities — this is what the raw-material gate-in flow uses to confirm an arriving truck's PO before recording vehicle details. Everything published here is live SAP read through the factory app; none of it is factory-app-owned data, so a SAP outage shows up as 502/503 rather than as empty results. A fourth area — a factory-app-native monthly Production Planning module (create plan -> weekly targets -> daily produced entries -> post to SAP) — is fully shipped in the web UI at /production/planning but its API is not deployed: every one of its 11 GET-capable endpoints returns 404 on all three companies. Nothing in this domain paginates.

### Traps

Verified live on OIL: summary 201 -> 201 (no change); details 201 orders/1127 lines -> 141/417; procurement 191 -> 59. Exposing it on the summary command ships a flag that silently does nothing, which is worse than not having it.

4) status IS honoured server-side on the plan dashboard even though the web UI never sends it (the UI filters client-side and explicitly strips status from its react-query key). Verified: OIL summary 201 -> 37 with status=planned, and a local count of the unfiltered payload gives exactly 37 planned / 164 released. Values are LOWERCASE planned | released.

## Quality control

*34 read commands · 26 write endpoints excluded*

Quality Control is the QA department's own workflow inside the factory app, and it holds three separate flows plus its own master data. (1) Raw-material inspection: when a truck's material reaches QA at gate-in, a QA "arrival slip" is raised against each PO item (particulars, billing qty, invoice/e-way/bilty numbers, COA/COQ attachments); once submitted it becomes an inspection, which is filled against the parameter list defined for that material type and then passes a two-step sign-off — QA Chemist first, QA Manager second — ending ACCEPTED, HOLD or REJECTED, and a rejected lot can be pushed into the return-to-vendor gate flow. (2) Production QC: in-process and final QC "sessions" taken on a production run that is currently running on a line; the FINAL session is the pre-dispatch clearance that gates FG release. (3) Online (in-line) Quality Monitoring: shift-wise readings taken on a filling line — pH, TDS, turbidity, alkalinity, hardness, torque per filling head, rub/closure tests — submitted and then approved or rejected. Behind all three sits master data: material types, the QC parameter specs per material type (NUMERIC / TEXT / BOOLEAN / RANGE with min, max, standard value and UOM), the SAP item ↔ material type mapping, and the document IDs printed at the bottom of QC report forms. Practically all the volume lives in JIVO_OIL (1,141 arrival slips, 1,101 inspections); JIVO_BEVERAGES has a small live set (95 slips) and JIVO_MART has almost nothing (8 slips, no material types) — the module is routed and enabled everywhere, Mart simply does not use it. Nothing in this domain is marketplace-gated, so there are no 403s here.

### Traps

1) NO PAGINATION ANYWHERE IN THIS DOMAIN. All 32 GET endpoints return a bare JSON array (or a bare object for the two /counts/ endpoints and every detail path) with no results/count/next envelope. A --page/--page-size flag would be meaningless and misleading here. Volume is real: /quality-control/arrival-slips/ on JIVO_OIL returns 1,141 rows / 1.2 MB and /quality-control/inspections/ returns 1,101 rows / 1.0 MB in a single response. The only narrowing that actually exists is from_date/to_date on the inspection lists and counts, status on arrival-slips, status on online-monitoring, final_status on completed inspections, line on the two run lists, session_type on run sessions, and search on material-types/sap-items.

2) workflow_status IS SILENTLY IGNORED. The SPA builds "?workflow_status=..." for every inspection list, but the server drops it. Verified twice on JIVO_OIL: /inspections/?workflow_status=DRAFT returned all 1,101 rows, and /inspections/completed/?workflow_status=DRAFT returned all 1,062. Never expose it as a flag — an operator would silently get the whole table back thinking it was filtered. Route stage questions to the dedicated sub-lists (pending / draft / actionable / awaiting-chemist / awaiting-qam / completed / rejected).

Every rejected inspection still has rejected_qc_return_entry_id = null, so nothing distinguishes them yet. 6) IDS ARE COMPANY-SCOPED AND A WRONG COMPANY LOOKS LIKE MISSING DATA. /quality-control/inspections/52/ is 200 on JIVO_OIL and 404 {"detail":"No RawMaterialInspection matches the given query."} on JIVO_MART. Same for material types. Any command taking an id must take the company that owns it, and a 404 on a detail call should be reported as "not in this company", not "does not exist".

7) FOUR-WAY 404 BODY PROBLEM. A route that does not exist returns an HTML page, not JSON — verified on /quality-control/po-items/80/qc/view, which returns a `<!doctype html>… Not Found` body. A route that exists with a bad id returns DRF JSON {"detail": "..."}, and a GET on a write-only path returns {"detail":"Method \"GET\" not allowed."} with 405. 9) by-sap-item RETURNS A LIST, AND THE CODE MUST BE UPPERCASE. /quality-control/material-types/by-sap-item/{code}/ returns an array of 0, 1 or many material types, not a single object. The SPA does .trim().toUpperCase() before sending; a lowercase code will miss. Empty array = "no material type mapping found for this SAP item", which is a legitimate answer, not an error.

## Returnable items

*14 read commands · 12 write endpoints excluded*

This is JIVO's RGP/NRGP gate-pass book — the register of material that leaves the factory gate and is meant to come back. A department raises a pass for a pump, motor, mould shaft, cutter, cooler, or a sample carton, says why it is going out (repair, exchange, calibration, job work, warranty claim, testing, demo) and who is holding it (an outside party like "Manoj electrical" or "Ak engineer Ganaur", or "Self"). The pass then walks a fixed lifecycle: DRAFT to PENDING_APPROVAL to PENDING_GATE_OUT to OUT, then PARTIALLY_RETURNED / RETURNED as the guard logs goods back in, then CLOSED — with CANCELLED and short-close as the escape hatches. Two document series live in one table: RGP numbers are returnable (something must come back), NRGP numbers are non-returnable (a sample or a giveaway that never returns), distinguished by the is_returnable flag. Each pass carries line items with an out-quantity, a returned-quantity and a running pending_return_qty, plus return events recording the vehicle, driver, transporter and security guard on both legs, plus photo/challan attachments. The three "pending-*" worklists are the actual desks people work from: pending-approval is the manager's inbox, pending-gate-out is the outbound guard's release queue, pending-gate-in is the inbound guard's list of material still sitting with an outside party. Everything an auditor needs — who submitted, who approved, who released it at the gate, who signed it back in — is on the gatepass detail and its timeline. The whole module is new since the July survey and is only being used by JIVO_OIL today.

### Traps

1. is_overdue IS A STALE STORED FLAG, NOT A COMPUTED ONE — this is the single biggest trap in the domain, and it is verified live, not inferred. Gate pass RGP/2026-27/000011 has expected_return_date 2026-07-28, is still status OUT with 1 unit pending, and reports is_overdue=false with days_overdue=6. The dashboard's overdue_count reads 0 on JIVO_OIL despite this. Consequences: (a) the list endpoint's overdue=true filter returns ZERO rows and a naive `--overdue` flag will tell an operator nothing is late when things are weeks late; (b) the dashboard overdue_count must never be quoted as the answer to "what is overdue?"; (c) the correct computation is expected_return_date < today AND status in (OUT, PARTIALLY_RETURNED), done client-side from the list or from pending-gate-in. Note days_overdue IS computed correctly and disagrees with its own is_overdue sibling — use days_overdue > 0, not is_overdue.

2. "ALL" IS A UI SENTINEL, NOT AN API VALUE. The frontend's param builder strips any value that is undefined, empty string, or the literal "ALL" before the request goes out. A generated command that faithfully forwards `--status ALL` would send a status the server has no row for. Omit the param instead.

3. /returnable-items/reports/ SILENTLY IGNORES HALF ITS PLAUSIBLE FILTERS. Verified by live row counts: status, date_from and date_to are honoured; purpose, is_returnable, overdue and q are accepted with HTTP 200 and no error while returning the completely unfiltered 40 rows. `?purpose=REPAIR` returned a first row whose purpose was TESTING. Any CLI that forwards the gatepasses filter set to the report command produces confidently wrong answers with no failure signal. Only wire status/date_from/date_to.

4. reports' date window is on the RAISED date, not the return date. date_to=2026-07-31 returned 39 of 40 rows, excluding exactly the pass created 2026-08-01 — so date_from/date_to filter created_at. An operator asking "what was due back in July" is not answered by this; they need expected_return_date, which reports cannot filter on at all.

5. DATA IS JIVO_OIL-ONLY TODAY, AND THAT IS NOT MODULE GATING. All 14 GET endpoints return HTTP 200 in all three companies — no 403, no WRONG_COMPANY, no 404. JIVO_MART and JIVO_BEVERAGES simply have zero returnable rows and an all-zero dashboard. Two consequences: never report "not available for this company", report "no gate passes recorded for this company"; and note that JIVO_OIL's own data contains departments named "production(beverages)" and "production(oil)", so beverages-plant gate passes are being raised inside the Oil company — switching Company-Code to JIVO_BEVERAGES to find them returns nothing. The only exception is sap-items, which reads the SAP item master and returns real rows in all three.

6. NO PAGINATION ANYWHERE IN THIS DOMAIN. Every list is a bare unwrapped JSON array containing the entire result set (the 40-row gatepasses list matches the dashboard's status_counts total exactly, proving it is not a truncated first page). Do not emit --page / --page-size for any command here. Three distinct envelopes are in play and a generator must not assume one: bare array (gatepasses, the three pending-* worklists, gatepass-items, return-events, attachments, sap-items, timeline), bare object (gatepass detail, dashboard, options), and reports' own bespoke {type, rows, count} wrapper which looks like DRF but is not — its count is a plain total with no next/previous and no page_size.

7. THE BUNDLE'S METHODS ARRAY UNDERSTATES THE READABLE SURFACE. HARVEST.json classifies /returnable-items/returnable-attachments/ as POST-only because the React app only ever uploads to it; the live probe returns 200 with 37 rows. Filtering the domain on the bundle alone would have silently dropped a working read endpoint. Conversely the flag direction that matters for safety still holds: 2 of the 14 published GETs (/returnable-gatepasses/ and /returnable-gatepasses/{id}/) plus attachments are dual-use, so the methods array — not any is_mutation flag — is what the write filter must key on.

8. NUMBERS ARRIVE AS STRINGS. quantity_out, quantity_returned, pending_return_qty, total_quantity_out/returned are strings like "2.000"; estimated_value and total_estimated_value are strings like "0.00" or null. Parse before any arithmetic or comparison, or "10.000" sorts below "2.000".

9. TWO DOCUMENT SERIES SHARE ONE TABLE AND ONE STATUS MACHINE. RGP/2026-27/nnnnnn is returnable, NRGP/2026-27/nnnnnn is not (is_returnable distinguishes them, 24 vs 16 on Oil). pending_return_qty is populated on NRGP rows too and is meaningless there — the UI renders an em-dash instead; NRGP/2026-27/000018 shows pending_return_qty "2.000" while status is CLOSED. Any "how much is still out?" total must filter is_returnable=true first, or it will overstate by every sample carton ever given away.

10. THE DASHBOARD'S OWN COUNTERS DO NOT RECONCILE WITH EACH OTHER. Live on JIVO_OIL: outstanding_count=5 but ageing_buckets sums to 3; outstanding_value=0 despite 5 outstanding passes, because estimated_value is null on every line item observed. 11. TIMESTAMP ZONES ARE INCONSISTENT ACROSS THE DOMAIN. Every endpoint returns IST (+05:30) except /returnable-items/reports/, whose rows carry UTC Z-suffixed timestamps for the same underlying fields. A pass gate-out at "2026-08-03T11:54:55+05:30" appears in the report as "2026-08-03T06:24:55Z". Normalise before comparing across commands, or a same-day event will look like it happened five and a half hours earlier.

12. IDs ARE NOT PASS NUMBERS. The detail, timeline and all the filter FKs take the integer PK (id), while humans quote pass_no ("RGP/2026-27/000023"). There is no lookup-by-pass_no endpoint; resolve via the list's q filter first. Related: /returnable-items/returnable-gatepass-items/{id}/ takes the LINE-ITEM pk, not the gate-pass pk — id 49 is a valid value for both endpoints and means two different things.

13. FIVE ENDPOINTS ARE REGISTRY-DECLARED BUT NEVER CALLED BY THE APP: options, reports, returnable-gatepass-items (both), and returnable-return-events. The React app hard-codes the enums in returnable.constants and reads lines/events/attachments nested inside the gatepass detail. They are live and genuinely useful to a CLI — they are the only way to sweep lines or events across all passes — but their parameter surfaces have never been exercised by a UI, and reports already proves what that costs (four filters accepted and ignored). Treat any filter on these five beyond the ones verified here as unproven.

14. PERMISSIONS ARE PER-ACTION, SO A TOKEN THAT LISTS MAY NOT DETAIL. The bundle defines returnable_items.can_view_returnable_gatepass, can_manage_, can_submit_, can_approve_, can_gate_out_, can_gate_in_, can_reject_at_gate, can_acknowledge_, can_close_, can_short_close_, can_cancel_. Only the view permission matters for this read-only CLI, but a 403 from these paths would be a genuine account-permission problem — unlike the marketplace 403s elsewhere in this survey, nothing in returnable-items is module-gated.

## Vehicles & drivers

*15 read commands · 0 write endpoints excluded*

This is the factory's transport master file plus the gate's vehicle-entry log. Three master lists sit under it — Vehicles (registration number, type, capacity, owning transporter), Transporters (contact person, mobile, GSTIN) and Drivers (mobile, licence, ID proof, photo) — and they are shared across the whole group: the same 528 vehicles, 114 transporters and 512 drivers come back whatever company you ask as. Vehicle Entries is the different animal: it is the gate log of every truck movement, one row per visit, and it IS split by company. Each entry carries a movement type (raw material in, sales dispatch/docking, daily needs, maintenance, construction, fixed asset, job work, empty vehicle) and a status that tracks it from DRAFT through the QC pipeline to COMPLETED. The count endpoint gives the same window broken down by status, which is what an operator wants for "how many raw-material trucks are still waiting on QC". Finally, vehicle history is a lookup by registration number that returns one vehicle's full dossier — every past visit across all three companies, the last driver seen with it, and the gate photos — used at the gate before linking a truck to a dispatch. Nothing here is a report; it is the raw operational record of who came to the plant, in what, and driven by whom.

### Traps

NO WRITE-ONLY (405) PATHS EXIST IN THIS DOMAIN — but 8 of the 15 paths are DUAL-USE and their write verbs are deliberately suppressed: POST on /vehicle-management/vehicles/, /vehicle-management/transporters/, /driver-management/drivers/ and /vehicle-management/vehicle-entries/; PUT on /vehicle-management/vehicles/{id}/, /vehicle-management/transporters/{id}/, /driver-management/drivers/{id}/ and /vehicle-management/vehicle-entries/{id}/. A reviewer should confirm the generated CLI publishes GET only on all eight. (The vehicleEntry API module also exposes a DELETE, but it targets RAW_MATERIAL_GATEIN.GATE_ENTRY_DELETE, which belongs to another domain group.)

1. REQUIRED PARAMS, DISCOVERED ONE AT A TIME. /vehicle-entries/ and /count/ both need entry_type + from_date + to_date; /list-by-status/ needs status + entry_type + from_date + to_date. The API reports only the first missing one, so a naive fix-the-error loop takes four round trips. All four errors use the {"detail": "..."} envelope (style 2 of the four in use). The current spec.yaml is wrong here: it omits `status` from list-by-status entirely and marks from_date/to_date optional there — both verified required live on 2026-08-03.

2. THE BASE ENTRIES ENDPOINT SILENTLY IGNORES status=. Verified live: /vehicle-entries/?entry_type=RAW_MATERIAL&from_date=2026-01-01&to_date=2026-08-03&status=QC_PENDING returned all 574 rows across five statuses. A CLI that just forwards --status to the base path returns unfiltered data and looks like it worked. Route to /list-by-status/ whenever status is supplied — that is precisely what the SPA's api module does.

3. THE entry_type ENUM IS BIGGER THAN THE UI. The Vehicle Entries page dropdown offers only 5 (Raw Material, Construction, Daily Needs, Maintenance, and SALES_DISPATCH labelled "Docking"). vehicle.constants adds FIXED_ASSET and JOB_WORK. And EMPTY_VEHICLE — which appears nowhere as a literal in the 575-chunk bundle — is accepted live and returns real EVGI- rows. An enum built from the UI dropdown would hide FIXED_ASSET, JOB_WORK and the entire empty-vehicle traffic. Only ONE value per call: the SPA fans out one request per type and concatenates; there is no comma or repeated-param support that I verified.

4. THE status ENUM IS ALSO BIGGER THAN THE UI, AND IS entry_type-DEPENDENT. UI dropdown: DRAFT / IN_PROGRESS / COMPLETED / CANCELLED. Live data adds QC_PENDING, QC_COMPLETED, QC_AWAITING_QAM, ARRIVAL_SLIP_REJECTED — the whole raw-material QC pipeline, which is invisible to the UI's own status filter. RAW_MATERIAL never uses DRAFT/IN_PROGRESS/CANCELLED; SALES_DISPATCH never uses the QC states.

5. MASTER DATA IS GROUP-WIDE, ENTRIES ARE COMPANY-SCOPED. /vehicles/, /vehicles/names/, /vehicle-types/, /transporters/, /transporters/names/, /drivers/, /drivers/names/ return byte-identical payloads under all three Company-Code headers (528 / 528 / 7 / 114 / 114 / 512 / 512 rows). Never print "Mart has 528 vehicles". /vehicle-entries/ and /count/ ARE scoped, and each row embeds company:{code}. A vehicle-entry id from another company returns 404, so "not found" usually means wrong --company.

6. VEHICLE HISTORY CROSSES COMPANIES. /vehicles/by-number/{n}/history/ returns the identical visit list under any Company-Code — verified with HR63E3409, which shows Mart DOCKV- dispatches while queried as JIVO_OIL. It is a group-wide dossier; do not caption it with a company name.

7. HISTORY USES A DIFFERENT SCHEMA AND A DIFFERENT TIMEZONE. Inside history, vehicle.vehicle_type is a string (not {id,name}), capacity_ton is a float 50.0 (not the string "50.00"), the transporter is flattened to transporter_name/contact/mobile/gstin, created_at is renamed registered_on, and every timestamp is UTC "…Z" — while every other endpoint in this domain returns IST "+05:30". Two commands rendering "the same" vehicle will disagree by 5h30m unless the CLI normalises.

8. NO PAGINATION, NO SERVER-SIDE SEARCH, ANYWHERE IN THIS DOMAIN. Every list is a bare JSON array with the whole table; no DRF envelope, no count/next/previous, so --page/--page-size would be meaningless. Tested live on /vehicles/: search=, page= and vehicle_number= are all ignored and still return 528 rows; same for search= on /drivers/. Any --search must be implemented client-side, mirroring the SPA's own filters. Budget for ~190 KB on vehicles and ~108 KB on drivers per call.

9. /vehicles/names/ RETURNS vehicle_number, NOT name. drivers/names/ and transporters/names/ return `name`. A shared "names" formatter keyed on .name silently prints blanks for vehicles.

10. VEHICLE NUMBERS MUST BE NORMALISED BEFORE THE PATH LOOKUP: uppercase and strip ALL whitespace, then URL-encode — exactly what the SPA does (trim().toUpperCase().replace(/\s+/g,"") then encodeURIComponent). "rj 47 ga 7522" will not match.

11. MASTER DATA IS DIRTY. Placeholder vehicles exist (00000, 123456789, BYHAND, BYHANDJONY, CASH) because hand deliveries and couriers are logged as vehicles. Transporter and driver names contain case-variant duplicates ('Courier' id 25 vs 'COURIER' id 43; three separate 'Amit' drivers). Join on id, never on name. gstin and remarks come back as empty strings rather than null.

12. entry_no PREFIXES CARRY MEANING and are a faster read than entry_type: GE- = raw-material gate entry, DOCKV- = sales dispatch / docking, EVGI- = empty vehicle gate-in, JWIN- = job work in.

13. DATE WINDOWS ARE INCLUSIVE AT BOTH ENDS (a same-day from=to window returns that day's rows), and a reversed window returns [] with HTTP 200 rather than an error — so an operator who swaps the dates gets a confident, silent "no entries".

14. NO ENDPOINT IN THIS DOMAIN SHOWS get_or_create BEHAVIOUR. The four by-id routes are integer-PK lookups on models with NOT NULL fields a GET cannot supply, and the entry detail 404s on a company mismatch. The by-registration-number history route is the only free-text key here, and the bundle proves it returns {found:false} plus a separate "Register this vehicle" POST button rather than creating — I did not send a novel number to confirm that branch live, as the rules forbid it.

## Warehouse — BST, BOM requests, FG receipts

*25 read commands · 26 write endpoints excluded*

The warehouse module is the factory floor's stock-handling desk — its own landing page calls it "Material requests, finished goods, branch transfers, and goods receipts". Three live workflows sit under /warehouse/. BOM Requests: production raises a material request against a run, the warehouse approves it fully or partly, then issues the materials. FG Receipts: finished goods coming off a production run are received into a warehouse and then posted into SAP. BST (Branch Stock Transfer): the newest and largest family — a BST is built from one or more SAP documents (a stock-transfer doc or a sales invoice), boxes are barcode-scanned out, the gate marks it out, it travels, the receiving branch scans it in and closes it, and any short shipment goes through a partial-transfer approval queue. Two small read-only master lists (/warehouse/wms/warehouses/, /warehouse/wms/item-groups/) survive from the old WMS sub-tree and feed the app's dropdowns straight from SAP. The eight WMS *analytics* endpoints live in July (stock overview, warehouse summary, batch expiry, billing overview, sales-order backlog, stock movements, transfers overview, dashboard) are gone — hard 404 in all three companies and no longer referenced anywhere in the bundle. What now carries the "WMS" name is a completely different physical warehouse-management app (rack rows/columns/levels, cell purposes, pallets, putaway movements) served from a separate /wms/ API root that is live in all three companies and was missing from the harvest entirely.

### Traps

1) STATUS FILTERING IS ASYMMETRIC AND SILENT. ?status= is a real server-side filter on /warehouse/bst/ (verified: 167 -> 115 rows, all RECEIVED) but is SILENTLY IGNORED on /warehouse/bst/incoming/ and /warehouse/bst/gate/expected-outwards/ (verified: ?status=RECEIVED returned all 98 rows with mixed statuses). Exposing --status on those two would hand an operator a filtered-looking answer that is not filtered.

2) UNKNOWN QUERY PARAMS ARE SILENTLY IGNORED — nothing 400s. Verified on /warehouse/bst/: ?source_type=INVOICE, ?search=BST-20260801-0010 and a deliberate garbage ?zzz_unknown_param=1 ALL returned the identical unfiltered 167 rows. So source_type and search do NOT exist on the BST list even though both fields are in the payload and both are searchable in the UI (the UI filters client-side). Only status, from_date, to_date are real there. Never infer a filter from a response field.

3) NOTHING IN /warehouse/ IS PAGINATED. Every list is a bare JSON array with no envelope and no page/limit support — /warehouse/bst/incoming/ returns 69 rows / 55 KB and /warehouse/bst/ returns 167 rows / 130 KB in one response. Date-range params are the only way to bound a result. A --page/--page-size flag would be a lie on all eight /warehouse/ lists. The separate /wms/ tree is the one exception and it is dual-mode: bare array by default, {results,count} the moment ?limit= is supplied.

4) SAP DocEntry IS PER-COMPANY. /warehouse/bst/sap-transfers/3475/ returned doc_num 826674501 dated 2026-08-01 in JIVO_MART and doc_num 225676542 dated 2025-02-06 in JIVO_OIL — the same key, two unrelated documents. Same for the internal integer ids on BSTs, BOM requests and FG receipts. Any command taking an id must carry the company with it, and an id must never be reused across a --company switch.

5) document_type DEFAULTS SILENTLY. /warehouse/bst/sap-transfers/{doc_entry}/ with no document_type behaves as STOCK_TRANSFER (verified). Reading an INVOICE-sourced BST's sap_doc_entry without ?document_type=INVOICE therefore returns the wrong document or nothing, with a 200.

6) ITEM-GROUP CODES DIFFER BY COMPANY. Verified live: CONSUMABLES = 101 in JIVO_MART and JIVO_BEVERAGES but 111 in JIVO_OIL; FIXED ASSETS = 110 in MART/BEVERAGES but 112 in OIL. Cross-company logic must join on NAME. Warehouse codes are likewise a per-company master (MART has GP-*, OIL has BH-CRUDE/BH-BT).

7) UI ROUTES ARE NOT API PATHS. The React app has routes /warehouse/grpo/material/pending, /warehouse/grpo/material/history/, /warehouse/grpo/preview/, /warehouse/invoice-approval and /warehouse-ops/* — none of them are endpoints. Verified: GET /api/v1/warehouse/grpo/material/pending/ and /history/ both 404, and so does the bare /api/v1/warehouse/. Material GRPO's real API lives under /grpo/ (another domain group). A generator that harvests router strings will invent a whole fake GRPO family here.

8) EMPTY IS NOT BROKEN. JIVO_MART returns [] for /warehouse/bom-requests/ and /warehouse/fg-receipts/, and JIVO_BEVERAGES returns [] for the whole BST family — all HTTP 200. The warehouse module is routed and enabled in all three companies; the data simply lives where the work happens (BST is overwhelmingly JIVO_OIL, 167 rows; BOM requests are OIL 95 / BEVERAGES 7 / MART 0). Never report an empty array as "not enabled for this company". There is no 403 anywhere in this domain — no module gating applies to warehouse.

9) TWO DIFFERENT THINGS ARE CALLED "WMS". /warehouse/wms/warehouses/ and /warehouse/wms/item-groups/ are SAP master lists (codes and names, for dropdowns). The /wms/* tree is a physical rack-and-pallet warehouse app with its own UUID-keyed records, and its inventory is floor-scan reality, NOT SAP stock — the two will not reconcile. Name the commands so an operator cannot confuse them.

10) /wms/cellPurposes/ is camelCase. It is the only camelCase segment in the API; normalising it to cell-purposes 404s.

11) THE WHOLE /wms/ TREE WAS MISSING FROM THE HARVEST. It is absent from HARVEST.json, from company-matrix-2026-08.tsv and from the app's frozen ENDPOINTS constant, because wmsStore builds its URLs from a bare base constant (`L="/wms"`) plus a template function rather than from the endpoints map. Anything else in this app built the same way is also invisible to the harvest — the constant is not, in fact, a complete index of the API.

12) DUAL-USE DENSITY IS HIGH HERE. /warehouse/bst/ is GET+POST, /warehouse/bst/{id}/ is GET+PUT, and every /wms/{collection}/ is GET+POST while every /wms/{collection}/{id}/ is GET+PATCH+DELETE. Filtering on an is_mutation flag would have admitted writes on all of them.

13) /wms/settings/ IS A GET-OR-CREATE PATTERN — but the create happens in the FRONTEND. Reading the bundle: getSettings() lists /wms/settings/, looks for a fixed singleton id, and if it is missing issues a POST itself. So the server-side GET is probably a plain list. I did NOT probe it and it is NOT published, because the marketplace incident was on exactly this shape and "probably" is not the bar for a live production API.
