# factory-cli 2026-08-11 — production area re-synced with the live app

Triggered by the new **Production → Execution → Line Management** screen. Every
fact below was verified live against `factory.jivo.in/api/v1` across all three
company codes on 2026-08-11. **Nothing was created on the live system.**

## Headline: the CLI was telling operators two things that are no longer true

1. **`line-configs` described the wrong data model.** It read *"the saved line
   presets (line + SKU + rated speed + labour/manpower counts)"* — one preset
   per line+SKU. Since **2026-08-05** the model is **many named presets per
   line, SKU optional**, maintained on Line Management and chosen by name when
   a run starts. Oil's presets carry no SKU at all (`1 LTR`, `2 LTR`, `5 LTR`);
   Beverages' do (`1 Ltr` → FG0000268).

2. **The domain guide said "OEE is not usable as a KPI".** True on 2026-08-03,
   when JIVO_OIL had zero line-configs and so no rated speed to divide by.
   Line Management is what closed that gap: **11 configs across 5 Oil lines**
   were created on 2026-08-05. Re-measured 2026-08-11 — **88 of 90 runs now
   return a non-zero performance, median OEE 46.2%**, against 0.4–2.2% before.
   Corrected in `DOMAIN-GUIDE-2026-08.md` entry 13, with the caveats.

**Added** — `GET /production-execution/line-configs/{id}/`, verified 200 on
JIVO_OIL (id 7) and JIVO_BEVERAGES (id 2). The SPA only PATCHes/DELETEs this
route; DRF serves GET on it, which the live probe proved.

**Descriptions corrected** — `lines`, `line-configs`, `line-configs-auto-fill`,
`runs`, `run-detail`, `costs-analytics`, `line-clearance-detail`,
`reports-analytics-downtime-pareto`. Each was checked against a real payload,
not just re-worded. Three claims from the domain study were **rejected** on
checking and rewritten: "cost per case" (the unit is cases but the figure is
usually unusable — see below), "observed: RUNNING" (the enum has five values),
and the auto-fill return shape (it wraps the config in `{"config": …}`).

## Traps now encoded in the CLI, found while checking

- **`per_unit_cost` is a trap.** It is `total_cost ÷ produced_qty`, and
  `produced_qty` is **0.00 on 72 of 148 Oil cost records (48%)** — including
  runs that plainly produced output (run 187 has a segment recording 200 cases,
  yet `total_production` is 0.0 and the cost record shows ₹24.9 lakh at
  per_unit_cost 0.0000). ₹1.50 Cr of costed value sits on zero-quantity
  records. **Never average `per_unit_cost` across records.**
- **Run segments are not a collection.** `GET /runs/{id}/segments/` → 404.
  Segments (and breakdowns) arrive embedded in `run-detail`. There is no
  segments command and there should not be one.
- **`runs` carries two statuses.** `status` (DRAFT / IN_PROGRESS / COMPLETED)
  is the record's lifecycle; `live_status` (DRAFT / RUNNING / STOPPED /
  BREAKDOWN / COMPLETED) is what the line is doing right now. They disagree
  routinely and answer different questions.
- **JIVO_MART has no production data.** Every production endpoint is routed and
  returns `200 []`. That is a data fact, not a scoping constraint — Mart is a
  trading company with no plant.

## Bug fixed: the MCP surface never substituted `{id}`

Found while verifying the new command end to end, and **pre-existing** — not
introduced by this change.

`handleCodeOrchExecute` resolved path placeholders from `ep.Positional` only,
which the press emitted empty for **108 of the 110** endpoints whose path
carries a placeholder. The literal `{id}` reached the request URL and the server
answered with an HTML 404, so every detail endpoint appeared not to exist when
called by an agent. The CLI was unaffected (it uses a different code path), which
is why it went unnoticed.

Fixed by binding placeholders through `TemplateParams` and then by name, and by
**refusing to send a request that still contains one** — a missing id now
returns an actionable error instead of a misleading 404. Pinned by
`internal/mcp/code_orch_pathparam_test.go`, which walks all 110 and fails if it
finds none. Written up as patch **0009**.

Scope is factory only: `exim-pp-cli` emits non-empty `Positional` for all six of
its placeholder endpoints and is unaffected.

## Four domains the CLI did not have at all

- **`supply-chain`** (17) — "Smart Supply Chain", the buy-and-build planner:
  grades every monitored material RED/AMBER/GREEN on days of cover against
  supplier lead time, turns a SAP forecast into a procurement list, checks the
  filling lines have the hours to run it, and reads SAP's open order book live.
  **It is unconfigured in all three companies** — no monitored SKUs, no lead
  times, no machines — so most endpoints return empty. That is a setup fact,
  not a fault, and the commands say so.
- **`order-processing`** (9) — mirrors OMS sales orders, checks each line
  against SAP stock, explodes the BOM and plans what to make and buy. Posts
  nothing to SAP. 2,281 orders live on Oil.
- **`goods-return`** (3) — customer returns coming back into the plant, through
  the gate and into the dedicated GR warehouses. Live and routed everywhere,
  no entries yet.
- **`activity-center`** (2) — who did what today, per user and per team.
  93 users, 13 active on the day of the sweep.

Plus 15 maintenance endpoints (daily electricity readings, wastage logs,
electricity meters, material-indent quotations), 6 `grpo/fg` finished-goods
endpoints, and detail routes across barcode, marketplace, vehicle and driver
management.

## Two shipped commands were pointing at routes that do not exist

`grpo history-detail` and `grpo service-history-detail` both carried the press's
placeholder description (`GET /grpo/history/{posting_id}/`) — a sign nobody had
ever verified them. Live check:

```
GET /grpo/570/          -> 200 JSON
GET /grpo/history/570/  -> 404 HTML   <- what the command was calling
```

Same for the service twin. Both **repointed** rather than duplicated: the names
are preserved (an operator's scripts keep working), the paths are corrected, and
both now return real rows. They had never worked.

This surfaced because the domain study proposed them as *new* endpoints, which
collided with the shipped names. A collision guard now refuses to apply any
addition whose command name already exists in git HEAD — writing it would have
silently overwritten two working command files rather than erroring.

## Deliberately NOT shipped

Five endpoints the studies flagged and the adversaries confirmed must stay out:

| Endpoint | Why |
|---|---|
| `/marketplace/settings/` | Confirmed Django `get_or_create` — a GET creates a row (patch 0007, correction C-0007) |
| `/marketplace/orders/resolve/` | Same shape, keyed on natural keys, never cleared |
| `/gate-core/sales-dispatch/lock/` | Suspected `get_or_create` on GET |
| `/blowing/runs/{id}/cost/` | In the registry but no read hook fires it; a GET here may write |
| `/barcode/dispatch/sessions/from-bill/` | The app's only call site is a POST |

These are enforced in the assembler's denylist on **normalised** paths, not by
prose — an exact-string denylist fails open on exactly the entries most likely
to have been renamed.

The 30 `WRONGLY_EXCLUDED` findings are recorded in `research/` for a human to
rule on. Most are adversaries catching a study that *omitted* an already-shipped
endpoint; because this change only ever adds, none of those were at risk.
